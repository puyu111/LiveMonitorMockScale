# livepipe 配置参数详解

一个 JSON 文件驱动整条流水线。本文件逐字段讲清 **类型 / 默认值 / 含义 / 对应的命令行参数**；
可跑的实例见 [`examples/pipeline.example.json`](examples/pipeline.example.json)。

三条总则：

1. **配置值 == 命令行参数。** 每个值都能对回原脚本的 CLI 开关（见「CLI」列）；`--dry-run` 会把配置还原成命令行打印出来，可逐字对照。
2. **相对路径相对 `base_dir`**（默认 = 运行命令时的工作目录，通常就是仓库根）。
3. **配置文件是 JSONC**：支持 `//` 行注释、`/* */` 块注释、末尾多余逗号。所以可以像示例那样**逐参数就地写备注**。（`_` 或 `$` 开头的键也会被当注释忽略——两种写法都认。）
4. 写错的键（拼写错）会打 stderr 警告但不中断。

> **代码位置（2026-10-27 拆分后）**：下文提到的判据函数/常量仍可从
> `livepipe/parse_live_comments.py` 导入，但该文件现在只是兼容 facade（re-export），
> 实现在 `livepipe/parsing/` 的分层模块里：文本规则 `parsing/text/`、版式 `parsing/layout/`、
> OCR `parsing/ocr/`、表情 `parsing/emoji/`、评论组装与去重 `parsing/comments/`、
> 面板定位 `parsing/panels/`、自检 `parsing/selftest/`。配置相关在 `livepipe/config/`。

## 🚩 两阶段工作流（本工具的核心用法）

**评论区范围是可变的**（视频号尤其），而定位只能说「这里有一片评论」，说不出「这是哪个平台」。
平台又决定 **行距 + 表情表**（抖音/视频号/微博/快手四套资产互不通用），填错就会整片认不出 —— 所以这一步交给人工。

```
① 定位    python -m livepipe panels cfg.json
          → 写出 panels.file，每个面板的 platform 留空（另附 _source / _locate_meta 取证）

② 标注    打开 panels.file，给每个面板填 "platform": "douyin" / "wechat"
          （可用平台 = 配置 platforms 段里的键；微博的档案见「表情表」一节的 ⚠️，当前写在 livepipe/征服8.json）

③ 解析    python -m livepipe run cfg.json
          → panels 步骤发现文件已存在 ⇒ 自动跳过（不会覆盖你的标注）
          → 按每个面板的平台取行网格与表情表，展开成 panels.resolved.json，再进 OCR/解析
```

> ⚠️ `panels.resolved.json` 是**派生文件**（每次 parse 前由配置按平台档案重写，`--only parse` 也会补写）。
> 它要是**跑到一半**被别人删掉（同一份输出目录跑了两条管线，另一条清空/重建了段目录），
> parse 只在 stderr 记一行 `[roi] ⚠ 面板文件不存在…`、把「badge_left 重算」和面板闸
> （rank_pill / fan_badge / badge_alias / overlay_cards / row_pitch）关掉继续跑，不再抛
> `FileNotFoundError` 把整条管线（连同后面所有段）带崩。**但结果会退化成「按旧行序几何」**——
> 看见这行警告就补跑一次。同一个 `output.dir` 上永远只跑一条管线。

面板文件长这样（人工编辑的就是它）：

```jsonc
{
  "panels": {
    "left":  { "rect": [575, 604, 1137, 1429], "platform": "douyin" },
    "right": { "rect": [1202, 1052, 1688, 1311], "platform": "wechat" }
  }
}
```

每个面板条目可写：

| 字段 | 必填 | 含义 |
|---|---|---|
| `rect` | ✅ | `[x1,y1,x2,y2]`，原图像素，OCR 的裁切窗口 |
| `platform` | ✅ | 平台名 → 决定行网格 + 表情表 + 裁切策略（见下） |
| `row_pitch` / `y_phase` / `x_text` | ✕ | 可选，覆盖平台档案里对应的值（同平台不同缩放时用） |
| `x2_from` | ✕ | 可选，覆盖平台档案的裁切右沿策略（`content` / `window`） |
| `rank_pill` | ✕ | 可选，覆盖平台档案的「等级标在昵称右边」（微博「榜N」药丸，见下） |
| `fan_badge_x_max` | ✕ | 可选，覆盖平台档案的「行首『粉丝』药丸被 OCR 并进正文」的几何闸（视频号手机 App，见下） |
| `badge_alias` | ✕ | 可选，覆盖平台档案的「行首**等级**药丸被 OCR 并进正文 ⇒ 同一个人的多种读法要归一」（视频号手机 App，见下） |
| `username_alias` | ✕ | 可选，覆盖平台档案的「昵称**末尾**被检测框切掉 ⇒ 同一个人被拆成两个账号」（视频号手机 App，见下） |

> 面板名（`left`/`right`/任意名字）只用来在日志与产物里区分，**不影响处理方式**；处理方式只由 `platform` 决定。

## 顶层

| 字段 | 类型 | 默认 | 含义 |
|---|---|---|---|
| `version` | int | `1` | 配置格式版本，必须是 `1` |
| `name` | string \| null | `null` | 只出现在日志里（不给则用配置文件名） |
| `base_dir` | string \| null | `null` | 相对路径的基准目录；`null` ⇒ 当前工作目录 |
| `platforms` | object | 见下 | **平台档案**：每个平台怎么处理 |

## `platforms` — 平台档案（不同平台走不一样的处理方式）

| 字段 | 类型 | 默认 | 含义 |
|---|---|---|---|
| `platforms.<名字>.emoji` | string \| null | — | → `emoji.tables` 里的键。决定该平台用哪张表情表；不填 ⇒ 该平台的面板不跑表情 |
| `platforms.<名字>.row_pitch` | float | — | 行距（像素，**可带小数**）。**兜底值**：解析时会从采样帧自标定（见下），只在证据不足时用它。⚠️ 别为了「好看」取整（`53.5` → `54`）：它逐行累加，取整那 0.5px 会在面板底部攒成半个行距的漂移，把相邻两条评论并成一行 |
| `platforms.<名字>.y_phase` | int | — | 首行中心距面板顶。**兜底值**：解析时**逐帧**自标定 |
| `platforms.<名字>.x_text` | int | — | 正文起始 x（徽章列右沿，**裁切内**坐标） |
| `platforms.<名字>.badge_span` | int | `58` | 徽章列宽：ROI 左沿 = `x_text − badge_span`（标注图/交付裁图的「圈」）。`58` 是桌面网页版实测；手机 App 的 `x_text` 落在药丸右沿**外侧**，要用更大的值（`douyin_app` = 74），否则 ROI 切在 `◆` 菱形上、等级标圈不进去。**不参与**徽章碎片判据 |
| `platforms.<名字>.x2_from` | `"content"` \| `"window"` | `"content"` | 裁切右沿怎么定，见下 |
| `platforms.<名字>.wrap_gap_ratio` | float | `0.73` | 续行间距比上限（≥1 个行距的是左对齐横幅）。一般不用写 —— 自标定 |
| `platforms.<名字>.x_ignore_from` | int \| null | `null` | 浮层（商品卡/预约按钮）左界：该 x 以右的文字不是评论。**写了就以写的为准**（自标定不覆盖，见下） |
| `platforms.<名字>.rank_pill` | bool | `false` | 等级标是**跟在昵称右边**的「榜N」药丸（微博）⇒ 行按药丸切成 昵称/正文，**药丸本身丢掉**。见下 |
| `platforms.<名字>.fan_badge_x_max` | int \| null | `null` | 行首有「粉丝」药丸徽章、且它**被 OCR 并进了正文**（视频号手机 App）⇒ 该面板行首徽章块的左沿上限，`null` ⇒ 不认这个徽章。见下 |
| `platforms.<名字>.badge_alias` | bool | `false` | 行首的**等级**药丸（`✦N`）有时被 OCR 并进正文 ⇒ 同一条评论被读成多种昵称、同一个人被拆成多个账号（视频号手机 App）。开 ⇒ 按几何见证把多种读法归一。见下 |
| `platforms.<名字>.username_alias` | bool | `false` | 昵称**末尾**被检测框切掉 1~2px（或末字漏读）⇒ `W.`/`W`、`期待sj`/`期待si` 被拆成两个账号（视频号手机 App）。开 ⇒ 按「同一条评论的两种读法同现」归一。见下 |
| `platforms.<名字>.account_key` | `"username"` \| `"nickname_level"` \| `"nickname_level_if_masked"` | `"username"` | **交付这一层按什么认人**：只看昵称 / 一律按 (昵称, 等级标 `◆N`) / **打码昵称**按 (昵称, 等级标)、不打码昵称只看昵称。见下 |
| `platforms.<名字>.wrap_at_text_left` | bool | `false` | **该平台没有左侧徽章列** ⇒ 折行续行与首行同左沿、形状判据失效，改按「与上一行的间距」认折行（微博）。见下 |
| `platforms.<名字>.wrap_indent` | int \| null | `null` | 已知的续行缩进量（像素）。一般不用写 —— 自标定；样本太少时才手填 |
| `platforms.<名字>.label` | string | — | 只给人看的说明 |
| `platforms.<名字>.colon_bg_max_v` | float | `110` | 像素找冒号时「还算暗底」的背景亮度上限。浅灰气泡底要让像素法工作就调大（`风云A9L.json` = 255）。见下 |
| `platforms.<名字>.colon_v_min` | float | `100` | 冒号点掩码的绝对亮度下限 |
| `platforms.<名字>.colon_v_delta` | float | `60` | 冒号点要比背景亮多少才算。浅灰底上的小彩点只亮 20~40 ⇒ 调到 30（`风云A9L.json`） |
| `platforms.<名字>.colon_text_fix` | bool | `false` | OCR 把冒号整个吃掉时，按像素冒号位置把「：」补回文本（救回用户名）。见下 |
| `platforms.<名字>.colon_text_fix_masked_only` | bool | `false` | 补冒号时**只认打码星号锚点**（`苗苗*` / `6**`），没有星号就不插。昵称后紧跟的标点会被 OCR 一起吃掉时（视频号），按字宽等分补会偏一格。见下 |
| `platforms.<名字>.strip_phrases` | string[] | `[]` | **本场专用词**（商品卡/浮层文字被 OCR 接在评论行尾）：parse 时按**后缀**剥掉；整行都是这些词时当作该行不存在（不打断续接链）。`08-08CTCC_抖音.json` 用。见下 |
| `platforms.<名字>.skip_phrases` | string[] | `[]` | **整行跳过词**：整行（忽略空白）等于其中任一词就丢掉这一行（公众号卡 `奇瑞汽车>` / 主题卡 `CTCC中国汽车场地职业联赛`）。只认整行，正文提到品牌名不受影响。`08-08CTCC_视频号.json` 用。见下 |
| `platforms.<名字>.merge_emoji_continuation` | bool | `false` | 纯表情续行并进上一条评论；`昵称：` 与「正文列起头的短昵称 + 表情」改判为纯表情评论。见下 |
| `platforms.<名字>.emoji_gap_sweep` | bool | `false` | 抽行时在相邻两行的**纵向空档**里补扫表情（长表情评论折行的第二行）。见下 |

内置两个（键名可改，也可以加新平台）：

```jsonc
"platforms": {
  "douyin": { "label": "抖音直播（等级标 ◆N）", "emoji": "douyin", "row_pitch": 68, "y_phase": 17, "x_text": 70, "x2_from": "content" },
  "wechat": { "label": "视频号直播（等级标 ✦N）", "emoji": "wechat", "row_pitch": 61, "y_phase": 21, "x_text": 60, "x2_from": "window" }
}
```

> ⚠️ **同一个平台可以有好几个档案**（版式不同就得各起一个名字）：内置的 `wechat` 量的是
> **网页版**（61 / 21 / 60）；视频号**手机 App**竖屏实测是 `50.6 / 25 / 30` + `fan_badge_x_max`
> + `badge_alias`，那套数字一个都不能照抄 —— 照抄行网格全错、整片认不出。手机 App 那一份是
> [`ctcc.json`](ctcc.json) 里的 `wechat_app`（含每个数字的实测证据）。
> 抖音同理：内置 `douyin`（68 / 17 / 70）是**桌面网页版**的，抖音**手机 App**竖屏实测
> `53.5 / 10 / 96`，那份是 [`风云T7.json`](风云T7.json) 里的 `douyin_app`。两者最要命的差别
> 在 `x_text`：手机版的**折行续行会缩进**到 x1≈37~45，正好落进药丸带 ⇒ `x_text` 必须取药丸列
> 的**右沿**（96），让续行落在「贴裁切左沿（`x_text−50` 以左）⇒ 一律算整行正文」那一支上，
> 才**不依赖** `wrap_indent` 自标定（这块素材的缩进续行自标定一段失败、一段误开成 0.95）。
> 同一份档案还带 `badge_span: 74`：ROI 左沿要退到药丸墨迹左沿（96−74 = 22），用默认的 58
> 只到药丸中段，标注图的框会把等级标的 `◆` 菱形切掉一半。
> 档案名不同不影响交付目录：`export_user_images.PLATFORM_CN` 把 `wechat` 与 `wechat_app`
> 都翻成 `视频号/`、`douyin` 与 `douyin_app` 都翻成 `抖音/`（**新增档案名要记得往那张表里
> 加一行**，否则会多出一个以档案名命名的目录）。

#### `rank_pill` — 等级标长在昵称右边时（微博）

抖音/视频号的等级标（`◆N` / `✦N`）在昵称**左边**的徽章列里，解析时按几何丢掉；微博的
助力榜标是「榜一…榜九」药丸，**跟在昵称右边**（`昵称 [榜五]：正文`），没有徽章列。不开
这个开关，药丸会被并进用户名（`甜甜蜜995榜九`）；冒号再被 OCR 吃掉时（`用户6861943086榜二
这车这么稳`）整行还会落进「续行」分支，把两个用户的评论搅成一条。开了之后按药丸切一刀，
昵称与正文各归各位，**药丸不记录在任何字段里**。

判据在 `parsing/text/classify.py` 的 `_RANK_PILL_RE` / `_split_rank_pill`，参数**量过**
（微博 16694 行全量）：名次只到「九」、一行最多一个「榜」、`榜` 从不出现在冒号之后 ⇒
切在药丸上不会伤到正文；药丸那截**最多一个字**且允许整个缺失（OCR 常把小字吃掉）。
**只在平台档案/面板条目里显式写 `true` 才生效** —— 它不走自标定，「药丸在昵称右边」是
版式事实，猜错就会拿形状去赌抖音的昵称与正文。

>抖音两套已交付语料（`out/comments_merged_v2`、`out/livepipe_example3`）上这个开关是关的，
>输出逐字节不变。

#### `fan_badge_x_max` — 行首「粉丝」药丸被 OCR 并进正文时（视频号手机 App）

视频号**手机 App** 的评论行首有一个「粉丝」药丸（关注了主播的人才有），它是**唯一一个
OCR 认不出是徽章的徽章**：数字等级标（`✦1`）要么被单独检出来当碎片丢掉，要么按 `_BADGE_RE`
从正文剥掉；而「粉丝」两个字既不是数字也不是标点，于是**并进正文块**
（实测 100% 是这个形态）⇒ 昵称变成 `粉丝踏雪归来`，交付名单里就是错的用户名
（参考交付语料 `2-2026-06-17艾瑞泽8…/视频号/` 里同一个人的目录名是 `踏雪归来-23`）。

判据要 text + 几何**两条**：文本以「粉丝」开头，**且**文字框左沿 `≤ fan_badge_x_max`。
为什么非要几何闸：真昵称也可能以「粉丝」开头（「粉丝团团长」），只按文本剥就把它的头两个字
啃掉 —— 那比不剥更糟（名单里的用户名是错的，而且跟这个人在别的帧里的读法对不上，会被算成
两个人）。同一个人的三种读法就吃过这个亏：`A-幸运小福星` / `1A-幸运小福星` / `+1A-幸运小福星`
（数字等级标并进正文；这一条的归一见 ``badge_alias``）。

闸门值量自两簇**互不重叠**的左沿（2026-10-09 CTCC 视频号素材，720×1600 竖屏，seg1+seg3
共 723 行）：徽章行 `x1 ∈ [32, 35]`（「粉丝」药丸自己的左沿）· 真昵称行 `x1 ∈ [38, 45]`
（没有药丸的昵称顶在正文列；有药丸的昵称被药丸顶到 84~95，更远）。取 **37** 夹在两簇中间。
整行就是药丸时（OCR 把它单独检出来了）行文本剥成空串 ⇒ 判 `drop 空行`：留着它会被当
**续行**粘到上一条评论的尾巴上（「粉丝」不是 junk）。

判据在 `parsing/text/badges.py` 的 `_FAN_BADGE_RE` / `_strip_fan_badge`。
**只在面板/平台档案里显式写才生效** —— 「这个平台的行首有没有这个药丸」是版式事实。

>抖音两套已交付语料 + 微博语料上这个键是空的，输出**逐字节不变**（重算校验过）。

#### `badge_alias` — 行首**等级**药丸被 OCR 并进正文时（视频号手机 App）

视频号手机 App 的评论行首有等级药丸（`✦N`）。它画在**昵称左边**，正常被当成徽章列里的
碎片丢掉；但 OCR 有时把它并进正文块 ⇒ 文字框从**药丸自己的左沿**起，药丸读数成了用户名
的前缀：`1A-幸运小福星` / `+1A-幸运小福星` / `★1A-幸运小福星` / `￥1A-幸运小福星` …
同一帧里读成哪种是随机的，于是**同一个人被算成好几个账号**。交付口径是「该账号 ≥3 条
正面评论」，被拆开就可能掉出名单。

**判据是几何见证，不是猜**：同一条评论被读成多种昵称时，**没并进药丸的那版文字框一定更靠右**。
实测（720×1600 视频号手机 App，2026-10-12，seg1 的 5620 行）：

| 读法 | 文字框左沿 `x1` |
|---|---|
| 并进了药丸（`1A-…` / `+1A-…` / `★1A-…` / `?1A-…` / `￥1A-…`） | 26~29（= 药丸自己的左沿） |
| 没并进去（`A-幸运小福星`） | 82~87（= 昵称列） |

同一个读法自己的抖动只在簇内 ≤3px，而两簇相距 **≥42px**；`MIN_GAP = 20` 夹在中间 ——
它同时把「OCR 丢了个行首字」（丢一个数字 ≈13px、丢一个汉字 ≈24px，长得像但不该归一）
排除在外。同一条评论实测最多被读成 **7 种**昵称。

取证做在 **rid 组**（滚动对齐给的「同一行」身份）里：组内取 `x1` 最大的那版当 canon，
要求它与「**别人**最靠右的一次」相差 ≥ `MIN_GAP`，且每一个别的读法都满足
「canon + 一个药丸 token」。药丸 token 按 **Unicode 类别**判（`?`(Po) `￥`(Sc) `★`(So)
`+`(Sm) 都是真实读出来的，写死字符表会漏），并且**含字母/汉字的一律不算**、
「光秃秃的两位数字」（`11`）也不算 —— `11天空` / `123亩176` 是真实昵称。

##### 判据升级：**等级标一致才算同一个人**（抖音手机 App，2026-10-14）

两条改动，都是为了让上面那条「两位数不算药丸」的保守闸门有出路 —— 抖音 App 的具名评论里
**21~25%** 带着并进去的药丸数字（`22阳***` / `29海***` / `16栀***`），`_is_badge_token`
一律不认，交付名单里同一个人仍是两个账号。

**① 等级标（`◆N`）现在是身份证据，不再是装饰。** 抖音 App 的 `◆N` 是**粉丝团等级**，挂在
人身上、与昵称绑定（实测同一个 `山***` 跨帧稳定读出 11）。所以「`11山***` 与 `山***` 是不是
同一个人」有了客观判据：**那位 `山***` 读出来的等级标是不是 11**。徽章块从前只留框、把读数
丢掉（`group_rows` 只记 `[x1,y1,x2,y2]`），现在连**读数**一起记（`badge_text`，检不出是
`None`，实测检出率约 **4 成**），并随行、随评论一路带到取证那一步。

**② 取证多了一条通道：跨 rid 的同一句话。** 实测「同一个人的两种读法」**几乎从不在同一个
rid 组里** —— seg1/seg6/seg7 三段切片里 **13 对全是**相邻但不同的 rid（`11山***` rid 115 /
`山***` rid 87、`19爱***` 112 / `爱***` 111…），两端正文一字不差。滚动对齐一重排就换 rid，
所以只认 rid 组的旧判据**永远看不见**它们。B 通道的判据是**三样一起**：

| 判据 | 取值 |
|---|---|
| 正文相同 | `norm_text(content)` 完全相等 |
| 几何 | 「没并进药丸」那版的 `x1` 比脏那版大 ≥ `MIN_GAP`（20） |
| **等级标** | 脏那版多出来的数字 == 干净那版**读出来的等级标** |

于是 `小明`（等级 6）与 `1小明`（等级 1）发了同一句话也**不会**被并 —— 这正是从前
「不敢按正文分组」的原因被消除掉的地方。A 通道同样吃等级标：形状不像药丸的两位数前缀，
只要等级标对得上就认（`22阳***` ➜ `阳***`）；**对不上就明确不并**，并在日志里留证
（`⚠ 等级标不一致，不并：…`）—— 那几行是唯一能看出「等级标被 OCR 读错导致误否」的地方。

等级标**读不出来**时（约 6 成的行）退回形状判据，与改动前逐字节一致；`_badge_digits` 取
数字前先过 `NFKC`（全角 `２９` → `29`），否则「读到了却比不中」。

> 已知取不到的档：脏读法把药丸**数字也丢了**时（`）海***`，菱形图标被读成全角括号、数字
> 没读出来）没有可比对象 ⇒ 不并（宁可漏归一）。几何上「横向伸进卡区」的长评论同理，
> 见 `x_ignore_from` 那节。

对照表拿到后**整块面板统一应用**，而不是只在取证的那一组里改：实测同一条评论
「这圈速可以啊…」被滚动对齐拆成了 **5 个 rid**，干净读法只落在其中两个组里，只改组内
等于没修（交付账号数 23→23）；全局应用后 23→22，`+1A-幸运小福星` 的 2 条评论并回
`A-幸运小福星`，评论总数一条不少。

> 为什么**不**按正文分组取证：实测同一条评论在「并进去」与「没并进去」两种读法下**正文
> 本身就不同**（并进去时 OCR 把尾巴也读全了：`这圈速可以啊，家用车 跑成这样` vs
> `这圈速可以啊，家用车`），按正文分组连见证都凑不到；反过来它还有**误伤真人**的风险 ——
> 两个不同的人碰巧都发「好看」，一个叫 `小明`、一个叫 `1小明`，就会被并成一个。

证据不足时**一个字都不改**（没配这个键 / 没有 rid / 差距不够 / 某组里混进了别人的名字
⇒ 只跳过那一组）。**残留**：字符级误读（`1A辛运小福星`、`A-羊运小福生`）不构成「后缀 +
药丸」的关系，几何判据救不了，也不该救（硬收敛会把两个人的话并给一个人）—— 这一档
现有的交付语料本来就容忍。

判据在 `parsing/text/badges.py` 的 `normalize_badge_alias` / `_badge_renames` /
`_is_badge_token` / `_badge_digits`（`MIN_GAP`）。**只在面板/平台档案里显式写才生效** ——
「这个平台的行首有没有等级药丸、它会不会被并进正文」是版式事实。命令行等价物：
`--badge-alias 面板名`。

>抖音 / 微博已交付语料上这个键是空的，输出**逐字节不变**（重算校验过）。

#### `username_alias` — 昵称**末尾**被检测框切掉时（视频号手机 App，2026-11-06）

比 `badge_alias` 低一层、同一条取证思路的另一类：「同一个物理行，在不同帧被读成**只差
一个尾巴**的两个昵称」。10.31 视频号实测三例（都是用户报的）：

| 现象 | 读法 A / B | 成因 | 全段行数 |
|---|---|---|---|
| 末尾句点被切 | `W.` / `W` | 昵称后 2×3px 的句点落在检测框外 | 192 / 68 |
| 末字整个漏读 | `李素熵` / `李素` | 同左，框右沿少框了一字 | 244 / 53 |
| 末字被切 1px 认成别的字 | `期待sj` / `期待si` | `j` 的降部画出框高 1px ⇒ 认成 `i`；滚到别的 y 框包住就对了 | 1343 / 42 |

第三例最关键：**同一份像素**，框高不同读出不同 —— 所以「按单帧选代表」治不了，只能按
**账号级多数写法**归一。交付层按昵称**原文字符串**认人（`account_id`），两种读法就成了两个
账号，各自算「≥3 条正面评论」而掉出名单。

**判据（取证）**：两个读法在**同一个 rid 组**里各出现 ≥2 次 —— 那是同一条评论在相邻帧的
两种读法，不可能是两个人；再放过一道**等级标硬闸**（两边都读到等级标且不一致 ⇒ 不并）。
允许的尾巴差异只有三类：

- 多 / 少**一个**末尾字（`李素` ↔ `李素熵`），且短名 ≥2 字（`王` ↔ `王强` 不认）；
- 多 / 少**一串纯标点**、≤3 个（`W` ↔ `W.` ↔ `W...`）；
- **等长**且 ≥4 字，只差**最后一个字**（`期待si` ↔ `期待sj`；二字昵称不认）。

**主写法**取**整个面板里行数最多**的那版（OCR 多数次读对）；平票才退到「更长 → 字典序」。
行首药丸那一类**不归这里管**（`+1八重樱` 的干净版是「文字框最靠右」的那版，按行数多数
反而会选中脏版 —— 两套判据相反，不能混）。

对照表同样**整块面板统一应用**（取证在某个 rid 组、改写要落到别的组；与 `badge_alias`
同理，必须跑在 `dedup_comments` **之前**，且排在 `badge_alias` **之后**）。

判据在 `parsing/text/badges.py` 的 `normalize_username_alias` / `_tail_variant`。
命令行等价物：`--username-alias 面板名`。没配这个键的面板**一字不动**。

> 这个键**不限于视频号**：抖音/快手/微博同样有「检测框切掉昵称末尾」的截断（抖音实测
> `15云时`/`15云`、`@晓物`/`@晓`、`淇淇她哥叫老昊`/`…老吴`，快手 `63350`/`63358`、
> `山药四地`/`山药四施`，都是同一句话、相邻时刻的两种读法）。仓库里的平台档案已全部
> 开启；没开的平台（或不配平台档案的纯文本用法）行为不变。

> 已知取不到的档：末字被切后认成**等长**的另一个字、且两边行数接近时，按多数选可能选到
> 错的那版（`宁远1869W` / `宁远18690` 实测 8 vs 15，末尾其实是一个橙色装饰字形，OCR
> 在 `W`/`0`/漏读之间摇摆）；账号合并本身是对的，只是交付名里那个装饰字不稳定。
> 行首药丸残留（`+1八重樱` 10 条、`+1无量塔姬子` 5 条）属于上一节，不归这里。

#### `account_key` — 交付这一层**按什么认人**（抖音手机 App，`风云T7.json`）

上面那些开关管的是「读到的**字**对不对」（药丸有没有并进昵称/正文）；这一个管的是更下游一步：
把评论归到一个**账号**时，凭什么说两条评论是同一个人。

| 取值 | 含义 |
|---|---|
| `"username"`（默认） | 只看昵称 —— 其他平台都这样：屏幕上的昵称是唯一的，同名即同一个人 |
| `"nickname_level"` | 按 **(昵称, 等级标 `◆N`)**：昵称相同、等级标不同 ⇒ **不是**同一个人 |
| `"nickname_level_if_masked"` | **打码昵称**（末尾星号，`爱**` / `用***` / 全角 `＊`）按 **(昵称, 等级标)**；**不打码昵称**仍只看昵称。一场里两种人混着出现时用 |

**为什么会要 `nickname_level_if_masked`（2026-11-08 用户定）**：同一场直播里往往
**匿名（打码）和非匿名（昵称完整）两类观众混着出现**（视频号：`爱**` 打码、`微风许甜`
不打码；抖音/快手某些场次只有一部分人被打码）。两类人要用**不同的**认人判据：

- 打码昵称 `爱**` 底下可能是几十个真人 ⇒ 必须靠等级标区分，「**匿名 + 等级标一致**」
  才算同一个人（等级标读不到 ⇒ 自成一档 `(昵称, "")`，不赌）；
- 不打码昵称本身唯一 ⇒ **不能**因为 OCR 把等级标读错/漏读就把同一个人拆成两个账号
  （旧的 `nickname_level` 一刀切会这样）。

**打码昵称的「名字一样」怎么判（2026-11-08 用户定）**：可见部分（星号之前露出来的那几个字，
通常就是第一个字，`account_id.visible_name()`）必须**逐字 100% 相同** —— `小***` 与 `健***`
是两个名字；星号个数被 OCR 读错**不算差异**（`小***` / `小**` 的可见名都是 `小`）。名字对上
之后，还要**等级标一致**（两边都读到且相同）才算同一个人；有一边没读到就不并。形近（相似度
≥0.7）、大小写、共用正文这些通道对打码名**一律关闭** —— 打码名底下本来就挂着几十个真人，
模板化直播里任意两个号共用一句文案是常态，那是噪声不是证据（`merge_segments/align.py` 里
按这个口径实现，`parsing/text/badges.py` 的段内归一同步）。例外是**药丸前缀**：`15木***` 是
「徽章列里的药丸 `15` + 昵称 `木***`」，剥掉后名字逐字相同，前缀数字就是这张行读到的等级标
（`promote_prefix_level`）。

实现：`account_id.level_of(comment, split_panels, masked_panels)` —— `masked_panels`
里的面板对不打码昵称一律返回 `""`（身份 = 昵称），对打码昵称返回 `badge_level()`。
配置链条：`platforms.*.account_key="nickname_level_if_masked"` →
`config.masked_identity_panels()` → `user_filter --identity-masked`（与
`--identity-panels` 并行；`qualify`/`collect`/`export` 读的是已拆好的 `level` 字段，不用再判）。
只有打码/不打码**混着出现**才需要这条；整场都打码仍用 `nickname_level`，整场都不打码用默认。

**为什么抖音 App 必须带等级标**：这块素材的昵称在屏幕上就是**打码**的（`用***`、`紫***`），
一个屏幕名底下可能是几十个真人；等级标（粉丝团 `◆N`）是屏幕上**唯一**能区分他们的证据。
只按昵称认人，等于把一堆陌生人的评论凑成一个账号。实测（两个 150 s 切片，`out/dyapp_v6y` /
`out/dyapp_v7y`；只量**账号划分**，「≥N 条」按**条数**算、不含情感判定）：

| 切片 | 评论 | 带等级标读数 | 账号：只按昵称 → (昵称, 等级标) | 其中「≥3 条」 |
|---|---|---|---|---|
| v6y | 108（匿名 19） | 48（44%） | 75 → **78** | 3 → **2** |
| v7y | 218（匿名 30） | 112（51%） | 131 → **150** | 14 → **7** |

老口径「≥3 条」的账号几乎全是**假的**：`紫***` 6 条其实是三个人（`◆26`×3、`◆14`×2、`◆15`×1）、
`一***` 4 条是四个人（`◆14`/`◆15`/`◆13`/`◆11` 各 1 条）—— 按老口径这四个人**合成一个合格账号**
交付出去（阈值 3，6 条和 4 条都过线）。反过来，读数**认不出**时宁可漏归一：没读到等级标的评论
自成一档 `(昵称, "")`，**永不**并进某个读到等级的档（上表 `小***`：无读数×2 与 `◆17`×2 是两档）。

**整段实测**（抖音 App seg6 = `17：13-17：33.mp4`，20 分钟，新 OCR 出 1983/6049 行带读数；
跑**真 CLI**（`user_filter` 两次）+ 既有判定缓存，零模型调用；阈值 = 本段 ≥3 条正面）：

| 口径 | 账号档位 | ≥3 条正面的账号 | 正面条数合计 |
|---|---|---|---|
| 只看昵称 | 244 | **32** | 397 |
| (昵称, 等级标) | 282 | **24** | 397 |

老口径那 32 个里，**8 个是「拆散后哪一档都不够 3 条」的** —— 也就是老口径把它们**凑**成了合格账号：
`海***` 老 4 条 = 无读数×2 + `◆18`×1 + `◆5`×1（三个人）、`霞***` 老 3 条 = `◆22`×2 + `◆2`×1
（一个 22 级和一个 2 级）、`我***` 老 3 条 = 无读数 + `◆16` + `◆8`。反方向**一个都没有**
（新口径不会凭空多出合格账号：拆开只会让合计变小）。

**怎么生效的**：档案里写了 `account_key`，`normalize_panels` 会把它带进各段的
`panels.resolved.json`；`config.identity_panels()` 读出这些**面板名**，自动填进
`user_filter --identity-panels`；`qualify` / `collect` / `export_user_images` 照同一份键合计。
**账号身份只有一处实现** —— `livepipe/account_id.py`（`account_key()` / `level_of()` /
`display()`），上下游都调它，别在别处重写。命令行等价物：`--identity-panels comments`。

**对交付物的影响**（改口径前先知道会变什么）：

- `users.jsonl` / `users_qualified.jsonl` / `merged_users.json` 每条多一个 `level` 字段；
- 目录名与名单行带上等级标：`用***◆16-3/`、`正面账号.txt` 里是 `用***◆16`
  （`account_id.display()`；没有读数时退回纯昵称，**跟老交付逐字一致**）；
- **改了认人口径就得连 `export` 一起重跑**：段里的导出目录是按旧口径切好的，`collect` 找不回
  新口径的目录会打 `[collect][warn] … 在各段导出目录里找不到图`（宁可吵，不静默丢人）。

**老语料怎么吃上这个口径**（2026-10-14 实测过，结论已改）：

读数**不止** OCR 行阶段一个来源，`parse` 阶段本身就会补两条证据，所以**只要 `rows.jsonl` 里
带药丸框**（`badge_text_of` 的输出就在行里），改完解析逻辑**重算 `parse` 即可，不必重跑 OCR**：

1. **跨帧凑**：`dedup_comments` 只留一帧代表一条评论，而留哪一帧按**正文清晰度**挑，跟徽章有没有
   检出来无关 ⇒ 拿**同一条评论的其它帧**上的读数去补（同昵称 + 多数决，平票不补）；
2. **顺手捡**：`normalize_badge_alias` 把**并进昵称的那截药丸数字**记进 `badge_text`
   （`13白***` 的 `13`）—— 能进对照表本身就过了取证。

全 7 段 T7 语料上实测：读数覆盖率 **22.0% → 39.6%**（3399/8588 条唯一评论有读数）。读到的值
**只补不改**（OCR 直接读数证据更强）。**只有**当 `rows.jsonl` 本身就早于药丸框（行里没这截证据）
时才需要重跑 OCR。

`初___-5/` 里 3 张 3 张无标 + 2 张 `◆11`、`白___-14/` 里 12 张无标 + `◆19`×1 + `◆21`×1）。

  变成幻影（`export` 只 mkdir + 覆盖，不 rmtree；脚本自己会清并逐条打日志）。
- 先印的**单子**包含：现状 vs 新口径的档位/张数、**档位有变的昵称**、`--show 昵称` 的逐图归属、
  以及**哪些档会因为拆开而不够阈值**（`0 < n < min_positive`，列出旧目录名）。落盘后按 **sha1 核账**
  （原地 / 换目录 / 掉档 / **凭空丢**），有「凭空丢」就非零退出。
- 想过线的人**变少**是**预期内**的（老口径的合格账号大半是假的，见上表）—— 想捞回被拆散的图，
  调低 `qualify.min_positive`（脚本会在单子里点名这些人），**别**把口径退回去。
- T7 实测一次：老树 298 档 / 2812 张（39 档带 ◆）→ 新树 301 档 / 2475 张（96 档带 ◆）；
  有 **407 张**掉到阈值以下（978 档带等级标里的 1126 张中一部分）。

#### `overlay_cards` — 评论列表上压着浮层卡时（视频号手机 App）

视频号手机 App 的评论 rect 里会**压着 UI 卡片**：通知卡（`通知欢迎来到直播间。直播间内禁止…`）、
平台提示卡（`色情低俗、诱导欺诈、抽烟酗酒等内容…`）、主题卡（`主题CTCC职业联赛鄂尔多斯站`）、
公众号卡（`公众号奇瑞汽车>`）、广告气泡（`奇瑞汽车` + `点击了解详情`）。它们不是评论，可它们
**长在评论 rect 里、又没有冒号** ⇒ 不判就被当匿名评论收进来、还画进验收图（实测 2026-10-12
CTCC：seg1 的 90 s 样本里 172 行有 **140 行**是卡，t=0 那帧产出的 3 条「评论」**全是卡**）。
微博那套 `_NOCOLON_NOTICE_RE` 一条都认不出它们。

取值两种写法：

| 写法 | 含义 |
|---|---|
| `true` | 只用**内置短语表**（`parsing/text/notices.py` 的 `_OVERLAY_CARD_RE`） |
| `"正则片段"` | 内置表 **＋ 这段**（本素材才有的词，见下） |

内置表只收「跟素材无关」的 UI 短语，且**只在没有冒号的行上**生效。卡片的**第二行**通常没有
任何特征词（主题卡的 `2026CTCC中国汽车场地职业联赛`、广告气泡的品牌行 `奇瑞汽车`），靠**卡片
续行**规则吃掉：命中卡片短语的行被丢之后，紧跟其后、同面板、槽位相邻的**一行**也丢（只吃一行
—— 卡是叠着排的，无限续链会把最下面那张卡底下的真评论一起吃掉）。

**品牌名这类词只能写在素材配置里**（写成字符串）。实测：`奇瑞汽车` 在抖音两套已交付语料的
无冒号行里命中 **25/40 行**，全是真评论的折行续行（`奇瑞汽车老品牌，值得信赖`）—— 放进内置表
就是拿品牌名赌内容。ctcc.json 里挂的两条是这素材广告气泡的实测形态：`奇瑞汽车`（OCR 把气泡
切成两行时，品牌这行什么特征词都没有）和 `^广?告[^知]`（气泡左上角的「广告」标签，有一帧
CTA 整行没读出来、只剩 `告奇瑞汽车`）。

**开这个开关还会带上第二条判据**（跨帧、不依赖任何词表）：「**列表滚了它没动**」的行也算浮层
（`frozen_overlay_texts`）—— 压在列表上的**固定**卡片（提示卡/商品卡）都符合，所以没写进短语
表的卡也丢得掉。反过来说：**跟着列表一起滚的卡**（抖音 App 的公告横幅 `风云T7全球品质纯电SUV
上市发布会，`）这条判据认不出，只能靠素材短语，见 [`风云T7.json`](风云T7.json) 的
`platforms.douyin_app.overlay_cards`（实测该横幅 x1 ∈ [94,97] 恰好压在 `x_text=96` 上 ⇒
不给短语的话它漏不漏由 1px 的 OCR 抖动决定）。

**只在平台档案/面板条目里写才生效**（版式事实，跟 `rank_pill` / `fan_badge_x_max` 同一条路）。
命令行等价物：`--overlay-cards 'comments=奇瑞汽车|^广?告[^知]'`。

#### `x_ignore_from` — 浮层压在评论列右边时（抖音手机 App，`风云T7.json`）

抖音手机 App 的商品讲解卡挂在**评论列右半边**（720 宽的裁切里 x1 ≈ 478~532），它有两个后果，
**同一条闸门一起消掉**：

① 卡上那几块文字**自己成行**（`讲解中` / `立即预`，没有冒号）⇒ 漏成匿名垃圾评论；
② 卡的文字块跟评论行落进**同一个行槽** ⇒ `assemble_row` 按 x 拼成一句
（`魏***：多少钱风云T7600k`，实测 s1 的 1927 行里 85 行 = **4.4%**）。②**不是**「OCR 并成一块、
分不开」——实测两块是分开检出的（评论 x∈[101,266]、卡 x∈[478,595]），只是被拼到了一起。

**取值方法（两簇之间的空带）**：把面板右半边的 OCR 块左沿做直方图，会看到两簇 ——
评论侧（含表情文字块 `互粉` x1=252 / `加油` 293，s7 的 `全球车` 316，**最大 325**）与浮层侧
（**最左 478**，`风云T7600k`；同卡还有 `讲解中` 488 / `稳稳的` 507 / `立即预` 532）。
中间 **[325, 478) 是 153px 的空带**，闸门取带子中间（`风云T7.json` 取 400，两边各留 75px）。
seg7 是 0.82× 的另一台设备，浮层是**放大版**卡（8 块，x1 394~465）、评论侧最大 316
⇒ 空带 [320, 394)、取 **360**（面板级覆盖）。全片 57 帧复量（每 60s 一帧）：评论侧最大 **324**，
浮层侧最小 **394~396**（`车型|风云T7`/`级别|紧凑型SU`/`续航|续航600H`/`能源|纯电动`/`风云T7600km` 全落在 396，
`讲解中` 414 / `立即预约` 438 / `600kn` 462）⇒ 空带宽 72px，360 两边各留 ~35px。

⚠ **seg7 有结构性代价（换任何设备/缩放下都可能遇到）**：这台机器的**长评论会横向伸进浮层的 x 区间**
（实测 `平***：看看车，总得选一款性价比高的` 是一条 x∈[82,437] 的块，而卡在 394~468 —— **两者横向重叠**）。
于是 OCR 有时把这一行切成「评论前段 + 卡块 + 评论后段」三块，**任何几何闸都分不开**：360 会连
「评论后段」（`价比高的`，x1 落在 400 上下）一起切掉。150s 切片的实测代价：
① 231 条里 **1 条真评论**被去重吞掉（`青***：电池安全有保障`，行两个 run 逐字节相同，
是 `assign_row_ids` 重排后 rid 撞车 —— 见 cerebrum 的同名条目，**与几何闸本身无关**）；
② **2 条**的代表读法成了截断版（`45盛大启幕！敬请期`、`看看车，总得选一款性`）—— 同一切片里
干净读法仍在（dedup 默认留**最早**的那次，而最早那帧正好被卡切开）。
净账仍是赚的（消掉的：卡自己的行 + 4 条真评论被还原），但这些代价要写下来。
**如果将来要更干净**：正解不是调这个数，而是让**卡的短语**去认卡（`overlay_cards` 加
`车型|风云T7|级别|紧凑型SU|续航|续航600H|能源|纯电动|讲解中|立即预约`），几何闸留着当兜底。

**为什么要写死、不能只靠自标定**（两段实测）：

* 浮层**只在一部分时间出现**（seg1 在 t≈314~370 才有），而自标定只 OCR **开头 4 帧**
  ⇒ seg1 那 4 帧里没有浮层、标不出界，整段裸奔；
* 标定值是「跨帧静止块的最小左沿」，而浮层最左那块**自己会飘 1px**：seg6 标到 **479**、
  实测它在 **478** ⇒ `x1 >= 479` 整块漏下来。**1px 之差**决定 4 条评论干不干净。

所以 `calibrate_panels` 现在**不覆盖手写值**（日志里留一行 `自标定浮层右界 x>=… ⇒ 保留档案值`
当证）。⚠ 改这条闸门时注意：仓库里没有别的配置写过这个键（`ctcc`/`csj`/`8PRO`/`exeed` 里出现的
都是注释里的 `"x_ignore_from": null`）⇒ 对既有语料是**逐字节空操作**。开关差分（`风云T7.json`）：

* **seg1 150s 切片**（该段 4 个标定帧里没有浮层 ⇒ 手写值原样生效）：评论 13 条 → **5 条**，
  去掉的 8 条全是浮层污染（`讲解中`、`立即预`、`***来了立即预`、`魏***：多少钱风云T7600k` ×2 …），
  4 条真评论一条不少，续行也没丢（`海***` 那条的两行读法被去重收敛成干净的一行）。
* **seg6 150s 切片**（该段标定**会**命中浮层 ⇒ 走的就是上面那条「不覆盖」的闸，日志实打实印了
  `[calib] comments: 自标定浮层右界 x>=479，档案已有 400 ⇒ 保留档案值`）：行数 1048 → 1047、
  浮层污染评论 **4 → 0**（`闲***：风云这段时间不活跃风云T7600k` → `风云这段时间不活跃`、
  `14幸***：给力风云T7600k` → `给力`、`冷***：风云T7600k` → 空正文 = 整条就是浮层），
  评论总数 111 → 111（**真评论一条没丢**）。

>抖音 / 微博的面板不开它 ⇒ 那两套已交付语料输出逐字节不变（量过：三套语料的无冒号行命中
>内置表 **0** 行）。

#### `colon_*` — 浅灰气泡底上的冒号（抖音手机 App，`风云A9L.json`，2026-11-01）

冒号检测有两条路：**像素**（同一列上下两个小点，见 `parsing/ocr/colon.py`）优先，OCR 文本里
读到「：」时按字宽插值兜底。像素法的默认假设是**暗底白字**：背景亮度中位数 > 110 就直接放弃，
点还要比背景亮 60。A9L 素材的评论气泡是**浅灰**（直播画面亮、气泡半透明，实测 V≈146~189），
默认参数下像素法整类失效 ⇒ 只剩 OCR 认冒号，而 RapidOCR 对 2px 小点经常整块不读
（本素材 **24~26%** 的行文本里没有冒号；风云T7 同类行只有 0~6%）。

* `colon_bg_max_v`: 255 —— 不再因「浅底」放弃像素法；
* `colon_v_delta`: 30 —— 冒号点实测只比背景亮 20~40（上点 V≈205、下点 ≈165、背景 146）；
* `colon_text_fix`: true —— 文本里没有冒号、但像素找到了位置时，把「：」**补回文本**
  （用户名/正文的切分只看文本里的冒号，光有 `colon_box` 只是画准了标注框）。
  落点优先用**打码昵称的星号串右沿**（`D***` / `T***`），没有星号才退回按字宽插值。

三个阈值键不写 ⇒ 与旧行为**逐字节相同**（既有语料零变化）。60s 切片实测（两段）：
用户名未识别从 24/45 + 34/58（53~59%）降到 10/34 + 19/41（29~46%）；剩下的多是冒号点
压在半透明滚动残影里、像素也找不到的行。

**视频号手机 App（2026-11-01，`风云A9L_奇瑞QQ/奇瑞汽车/风云新能原.json`）**：同一套阈值
（气泡底 V≈115~165，默认 110 会整段短路）。补字这一步要配
`colon_text_fix_masked_only: true`：视频号的打码昵称常只有**一个**星号（`苗苗*` /
`铠子*`），而且昵称后紧跟的标点会被 OCR 一起吃掉 —— 按字宽等分补会整体偏一格，
实测把 `梁，：内饰看着简约时尚` 切成 `梁内饰：…`、`平安：边吃饭边看` 切成 `平安边：…`。
masked_only 只认星号右沿（单星号也认），没有星号就不插。实测 0–115s 窗口：3 处补字
全部正确（`苗苗*：` / `铠子*：` / `6**：`），此前通用等分补出的 4 处错误切分全部消失。

另有一种行：**昵称块整块**没被 OCR 检出（正文块从 `x_text` 右边 ≥40px 才开始，如
`6**：比同级别合资强多了` 正文左沿 106、x_text 30），冒号落在正文框左侧。抽行/重画时
会向左多找一段（只放宽到 `x_text`，且点对必须紧贴正文左沿）—— **只补冒号框，不补字**
（昵称文本本身没读到，插冒号会把正文首字切成用户名）。

#### `strip_phrases` / `merge_emoji_continuation` / `emoji_gap_sweep` — 本场专用词与表情折行（抖音，`08-08CTCC_抖音.json`，2026-11-02）

这三个键只对**显式写了它们**的平台生效，既有语料不写 ⇒ 逐字节不变。

* `strip_phrases`：商品卡/浮层的文字被 OCR **接在同一行评论的末尾**（实测
  `白日梦游家：孙正16人已预约`、`几点开始艾瑞泽8PRO`、`16人已预约艾瑞泽8PRO`）。
  parse 时只剥**行尾**的同名短语（可连续多个）：
  `孙正16人已预约 → 孙正`；整行都是这些词（如卡片的 `艾瑞泽8PRO`）⇒ 当作这一行不存在，
  **不打断**上面的续接链；正文中间的真提及（`艾瑞泽8PRO真好看`）不动。
* `merge_emoji_continuation`：抖音的长表情评论会折成多行。修之前，第二行是**空文本行**，
  会被当成独立的匿名评论；而 `彭奶奶：`（正文就是后面的表情）会被 classify 判成**续行**，
  把不同人的评论粘成 `彭奶奶 铿锵玫瑰 毒舌猫猫头` 一条。开启后：`昵称：` 与
  「正文列起头的短昵称 + 表情」改判为纯表情评论；空文本的表情行按相邻槽位并进上一条。
* `emoji_gap_sweep`：表情扫描以**行文字框中心**、半个行距为半径；折行的第二行没有 OCR
  文字、又落在两条已检出行之间的空档里 ⇒ 扫不到（实测 t=160.1 的 `囍财` 表情评论：
  第一行 2 颗 [比心] 已认出，第二行 4 颗在它和商品卡文字行之间，整条只记了 2 颗）。
  开启后在空档里补扫，只收**中心落在空档内**、与上下两行已有表情不重叠的那些，并进上一行。

#### `skip_phrases` — 整行跳过词（视频号，`08-08CTCC_视频号.json`，2026-11-03）

`skip_phrases` 与 `strip_phrases` **分开**，因为两者剥的东西不同：

* `strip_phrases` 按**行尾后缀**剥：`白日梦游家：孙正16人已预约 → 孙正`。拿它剥品牌名会
  把真评论削掉（`我喜欢奇瑞汽车 → 我喜欢`）。
* `skip_phrases` 只认**整行**（忽略空白）：整行等于配置里的任一词就丢掉这一行。用于
  公众号卡 / 主题卡这种**整行都是 UI 文案**的行 —— 实测 `00020.1_roi.jpg` 的第 1 条
  （红框）是公众号卡：OCR 只读到 `奇瑞汽车>`（`公众号` 标签被吃掉），旧 parser 把它收成
  一条用户名空的「评论」；主题卡第二行 `CTCC中国汽车场地职业联赛` 同理。
  `小王：奇瑞汽车真不错` 这种**正文里提到品牌名**的真评论不受影响（整行不等于该词）。

配置写在平台档案里（按面板生效）：

```json
"skip_phrases": [
  "奇瑞汽车>",
  "奇瑞汽车",
  "公众号奇瑞汽车>",
  "CTCC中国汽车场地职业联赛",
  "2026CTCC中国汽车场地职业联赛"
]
```

⚠️ 裸词 `奇瑞汽车` 只在**本场素材里确认整行只出现在底部卡片带**时才收进来（本场实测：
y≈1180~1240、无冒号、socket 6/7）。换素材后若出现「整行只有品牌名」的真评论，把它删掉。
不带特征词、又分不清是不是卡片的行，交给 `overlay_cards` 的跨帧判据（列表滚了它没动）。

实现：`parsing/layout/paragraphs.py` 的 `_is_skip_line`（比较前去掉所有空白，
`公众号 奇瑞汽车>` 与 `公众号奇瑞汽车>` 视为同一行）；开关经
`ocr/overrides.py::_skip_phrases_panels` → `comments/build.py` 透传，
**不写这个键的面板与旧行为逐字节相同**。

#### `wrap_at_text_left` — 没有左侧徽章列的平台（微博）

抖音/视频号的续行**比首行更靠左**（首行左边有等级标徽章列），所以「形状」就能认出折行；微博
的续行跟首行**一样从正文列左沿起** —— 实测折行首块 `x1 ∈ [38,43]`、独立评论 `x1 ∈ [38,45]`，
**两簇完全重叠**，形状判据一个候选都挑不出来（同理，两条靠缩进/徽章的合并守卫在微博上也
恒为真/恒不成立）。开这个开关后改走**间距入口**：候选 = `x1 ≤ x_text + 8` 且**无冒号**的块，
去留由**同一个**「与上一行的间距」闸决定（折行 0.59~0.64 个行距 vs 紧随其后的独立评论
0.97~1.01，`wrap_gap_ratio` 0.73 正夹在两簇中间），认下的挂**小数行槽** `k±0.5` 再合并。

**挑不中的块照旧留成普通行**（跟抖音那条「形状不像就丢」相反）：微博这批候选里多数是
「冒号被 OCR 吃掉」的真评论，丢了就是真丢数据。**只在平台档案里显式写 `true` 才生效** ——
「有没有左侧徽章列」是版式事实，猜错会拿间距去赌抖音的独立评论。

判据在 `parsing/ocr/grouping.py` 的 `_text_left_candidates` / `parsing/layout/roi.py` 的
`_wrapped_socket`（间距闸复用 `parsing/ocr/lines.py` 的 `_is_true_wrapped_line`）。

>抖音两套语料开关关着 ⇒ 输出逐字节不变（微博：全片 91 对折行全部并上，逐帧评论数 −81，
>无内容丢失；见 bug-331）。

#### 面板几何自标定（`parse.calibrate`，默认开）

同一平台的**手机 App 录屏**和**桌面网页版录屏**是两套版式，数字不能通用：抖音网页版行距
68、续行**贴面板左沿**、续行间距 ≈0.63 行距；手机竖屏（720×1600）行距 ≈53、续行**缩进**
进徽章带、续行间距 ≈0.75 行距，且直播间浮层（商品讲解卡 / 预约按钮）压在评论列右边。

这些量**不必按录屏手填**：解析阶段会从几帧采样里量出来，覆盖档案里的兜底值（`--no-calibrate`
可关）。标定三个「跨帧不变」的量，**只在证据足够时改**，否则保留档案值：

| 量 | 怎么量 | 证据不足时 |
|---|---|---|
| `row_pitch` | 多帧「相邻评论首行」间距的中位数（首行 = 含冒号的行；续行/通知行不在格点上）。⚠️ **保留一位小数，不要取整**：槽位是「相位 + 槽号 × 行距」逐行累加的，53.5 取整成 54 会让每下一行多漂 0.5px，二十行就是 10px（0.19 个行距）—— 网格线正好落到两行中间时，两条评论会被并成一行（实测 seg4 十八帧：53.5 → 0 个并块，54 → 6.8%） | 置信度 < 0.6 ⇒ 保留档案值 |
| `x_ignore_from` | 跨帧**不动**、且落在面板右半边的文字块的最小左沿（浮层不滚动、评论滚动） | 找不到 ≥2 个 ⇒ 不设；**档案/面板里写了 ⇒ 一个字都不动**（量法见下） |
| `wrap_gap_ratio` + `wrap_indent` | 续行候选（无冒号、有文字、在正文列左边）到上一行的间距比；测到**缩进**续行才开。⚠️ 这里标定的是「**有**左侧徽章列」的平台；`wrap_at_text_left` 那类（微博）走另一个入口，不在这里开 | 样本 < 3 或不像续行 ⇒ 不动 |

行相位（`y_phase`）不在这里 —— 手机版面板**平滑滚动**、相位逐帧变，由主循环**逐帧**估；
网页版**整行滚动**、相位不变，逐帧估与一次性标定等价。

> ⚠️ **快手 App 要关掉自标定**（`parse.calibrate=false`）：快手评论之间夹着大量系统行
> （恭喜/送出灯牌/加入…），标定按「含冒号的评论首行」取中心，相邻两个首行**正好隔一条
> 系统行** ⇒ 行距被估成 2 倍（实测 `45.0 -> 90.8`，置信度 0.67 仍过闸）。后果不是「差一点」：
> 相邻两条评论被当成折行续行（用户名粘连/丢失），表情按 `0.667×90.8≈60px` 去扫 ⇒ **一个都
> 认不到**。快手配置里行距/相位/续行/浮层卡都已实测写死，关掉自标定最稳。
> 2026-11-04 实测：关掉后 seg1 前 60s 从「5 条评论、0 表情、3 条用户名丢失」变成
> 「5 条评论、4 条带表情共 11 个、0 条用户名丢失」。

#### 一行被网格线切成两槽时（`_merge_straddled_lines`）

OCR 常把一行评论切成两三块（昵称、正文、表情之间的空隙），块高不同 ⇒ 块中心差几个 px。
定槽是**逐块**做的（`snap_to_grid`），于是网格线正好穿在这个缝里时，同一行的两块会各自落进
相邻的两个整数槽 —— 一行变成两条评论。实测 seg4 t=0（`row_pitch` 53.8、该帧相位 ≈50）：
`***` 的 y 中心 504.5 → 槽号 8.448 → 槽 8，`167 161` 的 y 中心 508.5 → 8.522 → 槽 9。

后果不是「多一条空评论」这么轻：下游 `assemble_row` 各拼各的、跨帧去重按正文做 key 对不上 ⇒
交付里两张 ROI 一模一样（同一条 `[打call]×4` 算了两条、账号数虚高）；而且**被错位占掉的那一槽
本来是空槽**，`sweep_emoji_slots` 就不去补扫了 ⇒ 同一帧里真评论被吃掉（y≈1239 的 `[爱心]×4`
就是这么丢的）。

闸门只看几何、且**只在整数槽之间**做（折行/续行一律挂 `k±0.5` 小数槽，动不到它们）：两槽
中心差 < 0.30 个行距 **且** y 区间相交 ⇒ 同一条视觉行，合并后按整行块中心重定槽。0.30 这个数
同时把「并块行 + 它下面那条评论」和「相邻两条真评论」挡在外面（中心差 ≈ 一个行距）。

⚠️ 它**必须排在拆并块（`split_fused_rows`）之后**，所以挂在 `split_fused_rows` 的出口上，
不在 `group_rows` 里：拆之前那个槽里往往还压着下一条评论的块（实测 socket 9 里既有
`167 161`（y 496）又有下一条的 `***：`（y 548）），合并闸算出的「行中心」被拉低半个行距，
这一对就永远并不上。顺序反了一次实测过 —— 加了合并代码结果没变，就是栽在这里。

#### 纯表情评论的跨帧身份：表情集**一票否决**（`assign_row_ids`）

纯表情行的 `text` 是打码昵称残渣（`***`、`***1107 101`），`_row_key` 因此**一模一样**；跨帧身份
靠的是**整帧统一位移** `k`（逐行按 `prev[j+k]` 认亲）。一屏好几条纯表情评论时，位移差一格就把
**别人的评论**认成自己的 —— 而 `dedup_comments` 同一个 `rid` 只留最早一次，另外几条**整条消失**。
实测 seg4：t=6.87 一屏 `S***`×3，分别是 `[比心]×3` / `[爱心]×4` / `[打call]×4`，`rid=14` 一口气
串了三条 ⇒ 交付里比心整条不见（用户报的「比心没识别出来、也没圈出来」，`rows.jsonl` 里那行一直在）；
t=27.6 的 `[打call]×4` 同理。

判据很简单：**一条评论的表情不会变**。两行都是纯表情（`_emoji_sig` 非 None）且表情集**完全不相交**
⇒ 不认亲，另起 `rid`；先看上一帧 **±1 格邻行**里有没有表情集有交集的（整帧位移差一两格时会配到隔壁
那条，认邻行才对），邻行匹配带 `claimed` 集合、不抢已被认领的行。交集非空（只是个数识别抖动）仍算
同一条。

⚠️ 「正文为空」的判定**只认 `_is_junk`**（纯数字/标点/空白、OCR 一个字没读出来），别再多剥一步把
`S***` 里的字母也当残渣：全量 7 段 A/B 过，那一步只多出 seg4 t=27.6 的 1 条 —— 它和 t=6.87 是**同一条**
（被上一帧漏检），按位置继承后被 dedup 吞掉恰好是对的，等于凭空多一条重复计数、一个新评论也没救回来。

#### 空槽补扫的药丸只在**同一行**上（`sweep_emoji_slots`）

纯表情评论在行网格上是**空槽**（没有 OCR 行 ⇒ 没有「这一行」），靠 `sweep_emoji_slots` 在空槽上
造行补回来。它顺手要把行首药丸（菱形图标 + 粉丝团等级）并进 ROI 左边界 —— 药丸来自 `badge_col`，
而 **`badge_col` 是按槽位建的**：槽位一抖（`y_phase` 逐帧估、并块行错位），取到的就是**隔壁那条
评论**的药丸。实测 seg4：t=107.2 socket 10 的表情在 y 1315–1347，药丸却是 y 1376–1393 那条的。

后果两条，都是画面上看得见的：

- ROI 往下长出整整一个行距 ⇒ 交付图上**两个框叠在一起**（这条纯表情行 + 下一条评论）；
- `badge_text` 把**不相干的人**的等级标记进这条评论 ⇒ `_badge_renames` 拿它当身份证据去认人。

闸门只看 y：药丸中心与**表情簇中心**（不是槽中心）差 ≤ 0.5 个行距才并框、才读等级标；不同行就
`badge_box: None` / `badge_text: None`，ROI 只留表情框（`badge_left` 仍然兜左边界，所以左沿不会
因为丢了药丸而裁到内容）。宁可少一个等级标，也不能给错人。

#### `x2_from` — 裁切右沿怎么定（决定了会不会裁内容）

**背景**：裁切矩形是有两个身份的——它是「评论区」的语义区域，更是 **OCR 的裁切窗口**。
RapidOCR 在裁切边界上**不是平移不变的**：被边界切断的行会整行丢，或者更糟——**误读**。
实测视频号那条 `这品牌就是太实诚了，用料一直良心，五年…`，右沿定在 1688 时读成
`这品牌就是太实证`（尾字被裁后 OCR 补了个像样的胡说）。

| 取值 | 含义 | 适合 |
|---|---|---|
| `content` | 裁切右沿 = **内容右沿 + `pad_x`**（定位时按取样帧的并集定，之后固定） | 面板**固定宽**的平台（抖音）—— 裁得紧，OCR 省 |
| `window` | 裁切右沿 = **窗口右沿**（超集，按构造不裁内容） | 面板**右边跟着内容伸缩**的平台（视频号）。右沿若由内容定，定位那一刻定死的值后面必然裁内容 |

- 只有面板在**定位阶段**就已经有内容右沿可言时 `content` 才有意义；视频号那种「右边跟着内容走」的，
  唯一不裁的定法就是取窗口右沿。
- 代价：`window` 的面板裁切面积会明显变大（视频号面板实测 ×2.8，全片 OCR 约 **+38%**）。
- **`window` 会连带改 ROI 的算法**（见下），不是只改裁切。
- 窗口右沿从哪来：优先用定位产物里的 `_locate_meta.<面板>.window[2]`；手写面板文件没有它时用
  `panels.auto.frame_width` 兜底；都推不出来 ⇒ 不覆盖并打警告（此时右沿仍是内容定值）。

#### ⚠️ `x2_from: "window"` ⇒ ROI 右边界跟着换算法

裁切窗口放宽之后，**ROI 不能再用裁切边当右边界** —— 否则每条评论的框都会被拉到窗口右沿，
交付图上就是一片空白（这是回归，不是修复）。所以：

| `x2_from` | ROI 右边界 |
|---|---|
| `content` | 裁切边（= 定位时的内容右沿 + `pad_x`），全片一个定值 |
| `window` | **该帧内容右沿 + `pad_x`** —— 本帧所有行的「文字框 ∪ 表情框」最右值，即「面板在这一帧的真实右边界」 |

所以同一帧里的所有行共用同一个右边界（贴着这一帧的真实面板边），逐帧变化。
>`panels` 文件里每个面板也可以单独写 `x2_from` 覆盖平台档案（面板级优先）。

> ⚠️ `x_text` 是**裁切内**坐标（相对面板左沿）；换矩形会让它失效 —— 用 `panels.resolved.json` 里的
> `_apply_panel_override` 会按绝对锚点自动重算，所以手写面板一般不用管它。
> ⚠️ 几套表情表互不通用（抖音 214 / 视频号 109 / 微博 262）；平台填错 ⇒ 症状是「这一屏全是 `?`」。
> ⚠️ 微博的平台档案是 `platforms.weibo`（手机 App 竖屏：行距 74 / 相位 45 / `x_text` 38）。
> **档案跟着配置走**（不是全局注册表）：当前 checkout 里它写在 `livepipe/征服8.json`
> （那份 rect x1=10 ⇒ 档案里 `x_text` 取 **28**；38 按 rect x1=0 量。`x_text` 是裁切内坐标，
> 换 rect 要一起平移）。别的配置要在 panels 文件里填 `"platform": "weibo"`，得先把
> `platforms.weibo` 那段抄进自己的配置。只点表（`--emoji-table comments=weibo`，源名见
> `SOURCE_TABLES`）给不出行距，也给不出 `rank_pill` / `wrap_at_text_left`。

| `videos` | string \| string[] \| null | `null` | **多段素材**：同一场直播被切成几段录屏时一次配全（目录 / 通配符 / 路径数组），见下 | — |
| `segment_names` | string[] \| null | `null` | 段名（= 输出子目录名）；`null` ⇒ `seg1`、`seg2`…（个数须与段数一致） | — |
| `rows` | string \| null | `null` | 已有的 `rows.jsonl`：**复算**（省一次 OCR） | `--rows` |

| `duration` | float \| null | `null` | 处理多长（秒）；`null` = 整段 | `--duration` |
| `max_frames` | int \| null | `null` | 最多抽多少帧；`null` = 不限 | `--max-frames` |
| `interval` | float | `2.0` | 抽样帧间隔（秒），必须 > 0。**决定长跑时长**：全片 6294s ÷ 2s ≈ 3147 帧 ≈ 4.7h | `--interval` |

### 多段素材 `input.videos`

一场直播被切成几段录屏（手机录屏常见的「录到一半断了接着录」），用 `videos` 一次配全：

```jsonc
"input": { "videos": "/data/视频号/*.mp4" },        // 通配符（也可以给目录，或路径数组）
"output": { "dir": "out/ctcc" }                     // ← 这里是**段的父目录**
```

- 展开后按**文件名排序** = 时间顺序（录屏文件名普遍带时间前缀），段名依次是 `seg1`、`seg2`…
  想改名字用 `input.segment_names`（如 `["上午","午间","下午"]`）。
- 每段的输出落到 **`<output.dir>/<段名>/`**：`comments.jsonl`、`summary.json`、`rows.jsonl`、
  `panels.json`、`frames/`、`users.jsonl`… 于是每段自己是一份完整产物，可以单独复算、单独抽查。
- `<段名>/rows.jsonl` 已存在时**自动走零 OCR 复算**（改了解析逻辑重出结果不必再抽一遍行）。
- 面板：`panels.file` 在多段下**不生效**（一段一个 `<段目录>/panels.json`）；
  要显式指路用 `panels.files`（一段一项），或 `panels.manual` 写成**数组**（一段一项）。
  三者都不给时，`mode` 不写的自动判断会看**每一段**的面板文件在不在。

**步骤分两类**（见「`steps`」一节）：逐段步（`panels`/`parse`/`filter`/`export`/`draw`）
每段各跑一遍，全局步（`emoji_tables`/`qualify`/`collect`）整批只跑一次。
多段素材**串行**跑（内存有限，并行 OCR 会 OOM），管线本来就是串行循环。

跨段的两件事必须由管线**全局步**来办，不能各段自己办（详见 [`qualify` / `collect`](#qualify--export--collect--跨段与交付多段素材)）：

| 事 | 各段自己办的后果 | 谁办 |
|---|---|---|
| 合格判定（≥N 条正面） | 「seg1 两条 + seg2 两条」的账号在两段**各判掉一次** ⇒ 静默掉出名单 | `qualify`（按**合计**判） |
| 同名账号的目录 | `张三-2` / `张三-2-2` 两个目录 ⇒ 交付树里成了两个账号 | `collect`（并成一个、图号跨段连续） |

跑法（`--only` 点名即可，不必改文件）：

```bash
P=/home/puyu/anaconda3/envs/vlx/bin/python
HF_HUB_OFFLINE=1 TRANSFORMERS_OFFLINE=1 $P -m livepipe run cfg.json            # 抽行（免费、慢）
NLP_API_KEY=sk-xxxx $P -m livepipe run cfg.json --only filter,qualify,export,collect   # 筛→判→出图→拼树
```

### 抽帧策略 `input.sample`

固定 `interval` 同时踩两个坑：**静止时**对着一模一样的画面反复 OCR（白拍），**快滚时**又可能整条评论溜过两次拍摄之间（漏条）。按「面板内容的位移」抽帧能同时治这两个：

| `mode` | 行为 | 适用 |
|---|---|---|
| `interval` | 固定间隔（默认，行为与从前逐字节一致） | 短片段 / 需要可复现的固定帧 |
| `backoff` | 仍按 `interval` 抽，但**只在画面真变了才拍**、按变化自适应间隔 | `adaptive` 嫌重时的降级版；便宜，但对突发爆量只能事后反应 |
| `adaptive` | **顺序解码**，按面板位移/停稳/入口**内容触发**；只 OCR 触发了的面板 | 长录屏（推荐）：不漏且少重复 |

`adaptive` 的三个触发（每个面板各自判）：**位移安全网**（累计位移 ≥ 若干行 ⇒ 拍，保证不漏）、
**停稳触发**（动过之后静止几帧 ⇒ 拍，一次抓全一屏、且抓最清楚的那帧）、**入口触发**（没在滚
但底部入口行变了 ⇒ 判「新评论弹进来」⇒ 拍）；另加**超时兜底**。位移用面板 ROI 的**灰度行投影
互相关**估 —— 礼物/点赞动画不平移行网格，天然不触发。

| 参数 | 默认 | 含义 |
|---|---|---|
| `stride` | `1` | 每 N 个解码帧估一次位移（1 = 每帧都估） |
| `safety_rows` | `3.0` | 累计位移 ≥ 这么多行 ⇒ 强制拍（**上限 5**：跨帧对齐 `_best_shift` 的 `max_shift=8`，超了会让同一条评论被判成新行、重复评论冒到输出里）。实际阈值还会被**半个可见屏**收紧，短面板不漏 |
| `settle_frames` | `3` | 停稳多少帧后拍（主力触发） |
| `eps_px` | `1.0` | 相邻帧位移 < 它算「没动」（噪声地板） |
| `entry_thr` | `8.0` | 底带灰度均差 > 它且没在滚 ⇒ 判入口有新评论 |
| `max_gap_s` | `5.0` | 距上次拍超过这么久也拍一次（`0` = 关） |
| `min_interval` / `max_interval` | `0.2` / `6.0` | `backoff` 的间隔下限 / 上限 |
| `min_score` | `0.3` | 位移估计互相关下限；低于它当作「没有平移」（抗动画） |

`adaptive` 会把每次拍摄的瞬时位移写进行（`motion_px`）：跨帧去重时，同一个 `rid` 改留**位移
最小**（拍得最清楚）的那次，而不是最早的那次。`summary.json` 里 `sample_stats` 记每个面板各
触发了几次、按类别。

**纯表情评论（与表无关的行为约定）**：表情是图片，OCR 只认文字 ⇒「只有表情」的评论行
常常连打码昵称都读不出来。这种行要走完全程，靠三处配合（缺一处就是「表情认出来了、
评论却不存在、标注图上也不圈」）：

1. 有文字的行 —— 正常路径；
2. **只剩碎片**（`***`）的行 —— 只要这行认出了表情（`token` 非空）就当评论收下，
   正文空串、内容由 `emoji_text` 补；通知/系统行/浮层卡照旧丢（它们也常带表情）；
3. **一个 OCR 行都没有的空槽** —— 在**评论面板**纵向区间内（上下各内缩半个行距）的每个
   空槽上补扫表情，认到 ≥1 个**有名字**的表情（`token` 非空）才造一行，行框 = 表情框 ∪
   该槽的等级药丸。槽中心用**相邻单行插值**（并块/折行不当锚、两端按本地行距外推），
   不用标定相位 —— 手机 App 滚动时同一帧的相位还会上下分裂（实测 t=48.2 上半屏 −10px、
   下半屏 +16px），拿单个偏移扫会整排落在容差外。空槽闸门是**面板**而不是「必须有 ◆N」：
   纯表情评论恰恰是最没有药丸的那种，一帧能空一整排（t=49.2）。

ROI 取「文字框 ∪ 徽章 ∪ 表情框」的并集 —— 第 2 类的 OCR 框实测只有 10px 高，
只按文字框圈出来是一条细缝、表情全在框外。这三处都在 **`parse` 抽行那一刻**完成
（写进 `rows.jsonl`）：已有 `rows.jsonl` 走 `--rows` 复算**不会**补出新行或新表情，
要补必须重抽那一段（备份/移走 `rows.jsonl`，再 `--only parse`）。

### `panels.mode` 取值

| mode | 含义 | `panels` 步骤动作 | `parse` 步骤用 |
|---|---|---|---|
| *（不写 / `null`）* | **自动**：`file` 已存在 ⇒ `reuse`，否则 ⇒ `locate` | 同 reuse/locate | 同 reuse/locate |
| `locate` | **① 定位**：产出待人工标注的面板文件 | 定位并写 `file`（platform 留空） | `file`（经平台档案展开） |
| `reuse` | **② 复用**人工标注过的面板文件 | 无操作 | `file`（经平台档案展开） |
| `manual` | 手写面板（rect + platform）写进 `file` | 写 `file`（与配置不一致时按配置重写） | `file`（经平台档案展开） |
| `auto` | 解析时自己定位（需 GPU；无人值守快捷路径） | 无操作 | `--auto-panels <method>` + `auto.platforms` |
| `batch` | 批量定位 + 稳定性统计（挑固定矩形用；不动 `file`） | 跑 `batch_locate_panels` | 内置 `DEFAULT_PANELS` |
| `builtin` | 脚本内置 `DEFAULT_PANELS`（只对特定录屏有效） | 无操作 | 内置 |

> `mode=auto` 与 `input.rows` 冲突（复算时行已抽好，改矩形回不去）——配置校验直接报错。
> `mode=reuse` 时 `file`（多段：`files`，或每段的 `<段目录>/panels.json`）必须已存在；
> `locate` 在 `overwrite=false` 时**不会覆盖已存在的 file**；
> `manual` 下**配置是唯一来源**：file 只是落盘副本，配置里的 rect/platform 与它不一致就按配置重写
> （`overwrite=true` 时无条件重写；`draw_boxes.py --config` 也直接画配置值，见该脚本的说明）。
> **`mode` 不写（`null`）＝自动**：`file` 在就 `reuse`、不在就 `locate` —— 于是「先 `panels` 定位、填好
> platform、再 `run`」全程不用手改 `mode`（`overwrite=false` 也不会覆盖你的标注）。
> **多段素材**下每个判断都按**段**做：`mode` 不写时「**每一段**的面板文件都在」才判 `reuse`。
> `panels.manual` 写成数组时个数必须等于段数（校验期就报错，不会跑到第三段才炸）。

> 所以并行的单位只能是「同一帧里的行」；行与行之间没有依赖，因此开几个 worker 都不影响结果。

无冒号行，除了要「没被掩码昵称挡住」之外，还要**贴着上一条评论的最后一行**（≤ 0.85 个行距，
行距取面板的 `row_pitch`）才算折行续行。为什么需要：昵称被 OCR 整块吃掉时（视频号把昵称打码成
`**`，有些帧一个星号都没读出来 —— `萌萌：五站八冠，这统治力可以` + `线下有品鉴会就好了`），
**独立评论**的正文正好落在昵称列右边，形状和折行一模一样。实测两条评论按行网格排、间距 ≈ 一个
整行距，折行则 ≤0.76 ⇒ 0.85 夹在两簇中间。六套语料（抖音两套 + 微博 + 视频号三段）逐条 diff
过：418 对被挡下，其中 395 对正好 1.0 个行距、**0.76~0.85 之间一对都没有**（没有真折行被误挡）。
微博那 17 对尤其说明问题 —— 旧判据把 `榜N` 药丸开头的**另一个人**的评论并进了上一条。

**带冒号的折行**（手机 App 版**主播的两行评论**，`18：45盛大启幕！敬请期待！` 这种以时间开头
的第二行）：形状判据 `_is_wrapped_line` 一见冒号就当「昵称：正文」挡回去，于是第二行落成
**另一条评论**（昵称被读成 `18`），网格线卡在两行中间时还会并进首行、一个框圈两行。冒号那道闸
不能拆 —— 左对齐 + 带冒号的块里有**真评论**（昵称没有等级徽章、顶到面板左沿，实测 `苏***：
续航真够跑` x1=30）。所以这类块走**软入口**（`_colon_wrap_candidates`）：先留在普通行里，只有
**跟上一行 0.15~0.73 个行距**（和折行同一个间距闸）才摘出来当续行、挂**小数槽位**；过不了闸的
照旧是独立评论。下游 `parse_live_rows` 见到小数槽位就按**续行**处理（小数槽位只有一个来源 =
几何上已经证明是折行），文本层不再否决。

## `filter` — 评论 → 合格用户（大模型判定）

规则（2026-10-08 定）：

1. **用户名 ≥ `min_positive` 条正面评论**才算合格；「正面」由大模型**逐条**判定，
   **表情也一起发给它**（纯表情评论的 `content` 是空串，不看 `emoji_text` 就全成中性了）。
2. **用户名命中 `exclude_keywords` 的一律排除**（品牌/4S/门店/车型 + 官方侧姓名）。

默认**关**：这一步要花钱调模型。

| 字段 | 类型 | 默认 | 含义 |
|---|---|---|---|
| `enabled` | bool | `false` | 打开才会调模型 |
| `source` | string \| null | `null` | 评论来源；`null` ⇒ `<段目录>/comments.jsonl` |
| `out` | string \| null | `null` | 合格用户 JSONL；`null` ⇒ `<段目录>/users.jsonl` |
| `cache` | string \| null | `null` | 判定缓存 `judgments.jsonl`；`null` ⇒ 单段时落在评论同目录，**多段时全段共用 `<output.dir>/judgments.jsonl`** |
| `min_positive` | int | `3` | 用户名至少要有几条正面评论。**多段 + 开了 `qualify` 时这里会被强制取 `qualify.stage_min`**（各段这一刀必须最松，判定交给 `qualify` 按合计做） |
| `exclude_keywords` | string[] | 见下 | 用户名含任一即排除（不区分大小写） |

`nlp.*`：

| 字段 | 类型 | 默认 | 含义 |
|---|---|---|---|
| `api_key` | string \| null | `null` | 直接写 key（**别提交到仓库**）；留 `null` 则读 `api_key_env` |
| `api_key_env` | string | `"NLP_API_KEY"` | 读 key 的环境变量名 |
| `base_url` | string | DashScope 兼容模式 | OpenAI 兼容 `/chat/completions` 的 base |
| `model` | string | `"deepseek-v4-flash-0731"` | 判定模型 |
| `batch_size` | int | `20` | 一次调用判几条：越大越省，越大越怕一条坏整批 |
| `concurrency` | int | `4` | 并发请求数 |
| `timeout` / `retries` | float / int | `60` / `3` | 单次超时 / 重试次数 |
| `limit` | int \| null | `null` | 最多调多少批（控成本） |
| `prompt` | string \| null | `null` | 判定提示词；`null` ⇒ 用内置默认 |

**两处省钱机制**（都是精确的，不影响结果）：

- **按条数预筛**：「≥N 条正面」隐含「≥N 条评论」，所以评论数 < N 的用户**根本不可能合格**，不送模型。
  全片实测 6866 条评论里只有 2435 条属于「≥3 条评论」的 378 个用户，省掉 64% 的调用。
- **按内容去重**：判定结果按 `(content, emoji_text)` 哈希缓存到 `judgments.jsonl`。
  直播评论大量重复（`6666`、`支持` 之类），重复的只花一次调用；重跑不再花钱
  （实测 1469 条去重后 → 74 次调用）。

先估算再花钱：

```bash
python livepipe/user_filter.py --comments out/x/comments.jsonl --dry-run
```

**产出**（落在**段目录**）：`users.jsonl`（每个合格用户 + 他的逐条判定）·
`users.json`（汇总：候选数 / 合格数 / 调用数 / 被排除的用户名）· `judgments.jsonl`（判定缓存）。

> ⚠️ `api_key` 写进配置文件就等于明文落盘；优先用环境变量：
> `NLP_API_KEY=sk-… python -m livepipe run cfg.json`。

## `qualify` / `export` / `collect` — 跨段与交付（多段素材）

`filter` 之后到交付之间还有两步：先把各段**合起来判**合格，再把各段的图**并成一棵交付树**。
单段素材也能跑（`qualify` 退化成「按本段判」，`collect` 退化成「把这一段摆成交付树」），
所以出口只有一条路径，不必分情况。

顺序（`steps.order` 里也是这个顺序，**不能乱**）：
`filter`（逐段）→ `qualify`（全局）→ `export`（逐段）→ `collect`（全局）。

### `qualify` — 跨段判合格（全局步）

| 字段 | 类型 | 默认 | 含义 |
|---|---|---|---|
| `enabled` | bool | `false` | 是否跑这一步 |
| `min_positive` | int | `3` | **交付阈值**：账号在三段**合计** ≥ 这么多条正面才算合格 |
| `stage_min` | int | `1` | 各段 `filter`/`export` 用的阈值（这一步的回写定案后，各段照它出图即可） |

**为什么必须按合计判**：一个账号 seg1 两条、seg2 两条，合起来 4 条就该交付；各段自判「≥3」
会把它在两段各判掉一次 —— 名单上少了一个人，而且是**静默**少的（日志里看是「未达标」，事后极难发现）。
代价是判定量按合计算（实测约 ×2.6），所以各段 `filter` 的阈值被强制放到最松（`stage_min`）。

**动作**：读每段 `<段目录>/users.jsonl` → 按**账号身份**合计 `n_positive`（默认 `(昵称)`；
`platforms.*.account_key = "nickname_level"` 的平台是 `(昵称, 等级标)`，见上文同名小节）→ 写

- 每段 `<段目录>/users_qualified.jsonl`（只留合格账号，`export` 读它，少画一堆不要的图）；
- `<output.dir>/merged_users.json`（名单 + **每个账号各段各几条**，判合格的取证）。

缺任何一段的 `users.jsonl` 会**直接报错停下**（合计少算那一段，正好卡在阈值上的账号会被误判掉）。

#### 跨段账号归一（`qualify` 读表之后、合计之前）

解析层的 `normalize_badge_alias` / `normalize_username_alias` 只能在**段内**取证（同一条
评论的相邻帧）。段内一次干净读法都没有时（这个人只在 B 段被拍到，而 B 段每次都把徽章
读进昵称），同一个人就会在交付树里变成两个目录 —— `+1八重樱-11` / `八重樱-7`。
所以 `qualify` 在合计前先做一遍**跨段**归一（`tools/merge_segments/align.py`）：

1. **入围**：名字（忽略大小写）相似度 ≥0.7，或两者构成前缀/后缀关系。相似度只是候选。
2. **复核**（至少一条）：
   * **带数字的药丸前缀**（`+1`/`★1`/`￥1`/`14=`）⇒ 直接认 —— 真实昵称几乎不这么开头；
   * **货币符号前缀**（`￥63358`，快手粉丝团金币徽章被读成货币符号）⇒ 直接认；
   * **纯数字前缀**（`7用户6758305`/`11义节`/`163358`）⇒ 要共用正文 ≥1 条或数字 == 等级标；
   * **无数字的标点前缀**（`-`/`~`/`）`/`？？？`）**不算药丸** —— `-风-`、`~龙姐` 这类
     真实昵称很常见，必须叠加「只差一个字符 + 共用正文 ≥2」才并；
   * **只差一个字符**（`路顺风`/`一路顺风`、`谯蕉美食`/`谯谯美食`）⇒ 共用正文 ≥2 条；
   * **仅大小写不同**（`Vkgkgnf`/`vkgkgnf`）⇒ 直接认。
3. **等级标硬闸**：两边都读到等级标且不一致 ⇒ 不并。
4. **主写法**：药丸前缀 ⇒ 选被加前缀的那版（`八重樱`、`63358`）；否则选评论条数多的
   （平票按更长、再按字典序，保证确定性）。改写**整批跨段应用**，不只取证那一段。

没通过复核的对原样保留，日志里留证：`[align] ⚠ 不并：A / B（原因）`。

### `export` — 逐段出交付图

| 字段 | 类型 | 默认 | 含义 | CLI |
|---|---|---|---|---|
| `enabled` | bool | `false` | 是否跑这一步 | — |
| `base` | `"frame"`\|`"annotated"` | `"frame"` | 底图：视频原帧（交付形态）/ 解析期画的标注图 | `--base` |
| `labels` | string | `"正面"` | 出哪些标签的评论（逗号分隔） | `--labels` |
| `min_positive` | int \| null | `null` | 出图阈值；`null` ⇒ `qualify.stage_min` | `--min-positive` |
| `min_scope` | `"platform"`\|`"global"` | `"platform"` | 阈值算在哪一层：平台内各自够数 / 整段够数 | `--min-scope` |
| `users` | string \| null | `null` | 合格用户表；`null` ⇒ `<段目录>/users_qualified.jsonl`（没有就退回 `users.jsonl`） | `--users` |
| `frames` | string \| null | `null` | 标注图目录（`base=annotated` 时用）；`null` ⇒ `<段目录>/frames` | `--frames` |
| `color` / `width` | string / int | `"0,255,0"` / `3` | 绿框颜色/线宽（对齐参考语料） | `--color` / `--width` |
| `pad` / `pad_ratio` | int / float | `0` / `0.25` | 框外扩（紧贴评论行还是留白） | `--pad` / `--pad-ratio` |
| `quality` | int | `90` | JPEG 质量 | `--quality` |
| `force` | bool | `false` | 目标目录非空也照写（默认报错退出） | `--force` |

产出：`<段目录>/<平台中文名>/all_users_正面_<阈值>张以上/<账号名>-<本段条数>/1.jpg…`
（目录名是**本段**的条数；跨段同账号目录由 `collect` 并成一个）。账号名默认是昵称，
`account_key = "nickname_level"` 的平台带上等级标（`用***◆16-3`，见 `platforms.account_key`）。

### `collect` — 拼最终交付树（全局步）

| 字段 | 类型 | 默认 | 含义 |
|---|---|---|---|
| `enabled` | bool | `false` | 是否跑这一步 |
| `stage_min` | int \| null | `null` | 各段导出目录名里的数字；`null` ⇒ `qualify.stage_min` |
| `platform_dir` | string \| null | `null` | 交付树里的平台目录名（`视频号`…）；`null` ⇒ 从各段导出目录自动认 |
| `out` | string \| null | `null` | 交付树根；`null` ⇒ `<output.dir>/<平台目录>/all_users_正面_<合计阈值>张以上` |
| `force` | bool | `false` | 目标非空时整棵重来（默认报错退出） |

**动作**：按**账号身份**把各段的 `<账号名>-<本段条数>/` 并成一个 `<账号名>-<合计条数>/`，
图号 `1.jpg…N.jpg` **跨段连续**（按段顺序 = 时间顺序），再写 `正面账号.txt` + `manifest.json`
+ **`README.md`**。
那份 `README.md` 是给**拿到交付的人**看的（目录名里的 `◆N` 怎么读、哪些目录是「没读到等级标」、
本批账号/张数/分段账），由 `collect` **生成**、数据全从当次的 `doc` 现取 —— 因为这棵树每次
collect 都被 `rmtree` 重建，**手写一份放进去下次就没了**，而它恰好是那套命名的唯一说明。
`manifest.json` 里带每段的段名/视频/输出目录与图数核对（`mismatch` 非空就是图数对不上合计）；
`users[]` 与各段 manifest 一样**多一个 `level`**（`account_key` 生效的平台才有值）。
合计合格、却在各段导出目录里找不到图的账号会打 `[collect][warn]` —— 那说明**认人口径变了而
`export` 没跟着重跑**，不是「这个人这轮没合格」。

某一段**一个可交付用户都没有**时，`export` 只印一句「没有可交付的用户」、连
`<段目录>/<平台>/all_users_…张以上/` 都不建 —— 所以 `collect` 找不到目录时先看该段的
`users_qualified.jsonl`：**存在且为空**（`qualify` 每段都会写，哪怕 0 行）⇒ 该段确实 0 人，
打一行 `[collect][note] … ⇒ 跳过该段` 继续拼树；文件缺失或非空才是「`export` 没跑完」，
照旧报错中止。

`manifest.json` 的 `users[]` **除了** `username/dir/count/segs`，**还有 `images`** —— 逐图那一条
（`t`/`roi`/`label`/`content`/`emoji_text`…）照抄段 manifest，只把 `rel` 重写成**合并树里**的路径
（`<目录名>/<新图号>.jpg`）、另加 `seg` 记来自哪段。**为什么必须带**：交付树这个路径与单段 `export`
同名（`<output.dir>/<平台>/all_users_正面_<N>张以上/`），下游按「逐图清单」读它（`mock_scale` 的扩展线
就是）—— 只写汇总的话，同一个路径换了个生产者就崩在 `KeyError: 'images'` 上（bug-356）。图是 `copy2`
来的、与段里那张同字节，所以段 manifest 里的 `roi` 对合并后的文件**逐张成立**。

> 平台目录名靠 `export_user_images.PLATFORM_CN` 把平台键翻成中文；**同一个平台的不同档案名**
> （如视频号网页版 `wechat` 与手机 App `wechat_app`）要在那里各列一行 —— 漏一个就会多出一个以
> 档案名命名的目录。

## `steps` — 步骤编排

| 字段 | 类型 | 默认 | 含义 |
|---|---|---|---|
| `order` | string[] | 见下 | 执行顺序（可重排；未知步骤报错） |
| `skip` | string[] | `[]` | 跳过的步骤 |

默认 `order`：

```jsonc
["emoji_tables", "panels", "parse", "filter", "qualify", "export", "collect", "draw"]
```

| 类别 | 步骤 | 跑几遍 |
|---|---|---|
| **逐段** | `panels` · `parse` · `filter` · `export` · `draw` | 有几段就跑几遍（多段素材下日志里写 `parse · seg1`…） |
| **全局** | `emoji_tables` · `qualify` · `collect` | 整批一次（它们要看**所有**段的产物） |

顺序有**依赖**：`filter`（逐段）→ `qualify`（跨段判合格）→ `export`（逐段）→ `collect`（拼树）。
重排时别把它们分开。

命令行 `--only a,b` / `--skip c` 可**临时覆盖**（不改文件）。

> `--only` **点名的步骤一律执行** —— 配置里的 `filter.enabled = false` 意思是「默认这一趟别跑」
> （多半因为要花钱 / 要 GPU），不是「永远不许跑」。否则 `--only filter` 会静默跳过 filter，
> 下游 `qualify`/`export`/`collect` 全部空转着「跑完了」（最坏的一种失败）。
> 被这样打开的步骤会在日志头部点明。
> ⚠️ 但 `--only` **拉不回 `steps.skip` 里的步骤**（skip 先算）—— 想让某步永远靠点名跑，
> 就别把它放进 `skip`。同理，`--skip` 优先于配置里的 `order`。

## 常见组合

```jsonc
// ① 两阶段：先定位（产出待标注面板文件）
{ "input":  { "video": "V.mp4" },
  "panels": { "mode": "locate", "file": "out/x/panels.json" } }
// ② 人工填 platform 后，改成 reuse 复用（或直接重跑：文件已存在不会再定位）
{ "input":  { "video": "V.mp4" },
  "panels": { "mode": "reuse", "file": "out/x/panels.json" } }

// ③ 全片长跑（复用已标注面板、关标注图）
{ "input":  { "video": "V.mp4", "interval": 2.0 },
  "panels": { "mode": "reuse", "file": "out/x/panels.json" },
  "output": { "dir": "out/full", "frames": false, "rows": true } }

// ④ 改了解析逻辑后复算（不重跑 OCR）
{ "input":  { "video": "V.mp4", "rows": "out/full/rows.jsonl" },
  "panels": { "mode": "reuse", "file": "out/x/panels.json" },
  "output": { "dir": "out/full" } }

// ⑤ 手写面板（跳过定位模型）
{ "input":  { "video": "V.mp4" },
  "panels": { "mode": "manual", "file": "out/x/panels.json",
              "manual": { "left":  { "rect": [575,604,1137,1429], "platform": "douyin" },
                          "right": { "rect": [1202,1052,1688,1311], "platform": "wechat" } } } }

// ⑥ 无人值守快捷路径（平台固定，省掉人工那一步）
{ "input":  { "video": "V.mp4" },
  "panels": { "mode": "auto",
```
