1 · livepipe 已经算好、mock_scale 还在重算的那部分

comments.jsonl（每段一条，与 rows.jsonl 同目录）是最直接的索引：一条评论一个对象，导出图的 roi 就是它的 roi，按 roi 精确匹配实测 73/73。退一步用 rows.jsonl 也行 —— 一行 = 一帧里的一条评论行（全帧原图像素），导出图的 roi 实测等于 [badge_left, min(box.y1, badge_box.y1), x_right, box.y2]（多行取并集；这张例子里 min(1456, 1455) 正好是 roi 的 1455）。两条路都不重跑 OCR、不读一个像素。

2 · 能替什么、不能替什么（实测划界）

✅ livepipe 更准或独有 —— 应当直接用❌ 只能由像素量 —— 用了反而错
  • 等级：badge_text，纯数字 25/25
  • 身份：rel/t/panel，比 mtime 稳
  • 行结构：一张图里几行、是否续行
  • 冒号位置：独立的第二意见
  • 有没有徽章：旁证（badge_box 非空）
  • 整颗药丸：OCR 框实测 13~50px 抖动；抖音药丸在 17 张认定成功的图里 15 张是 57px（另 2 张 56/46），与等级无关
  • 名字墨宽 slot_width、字带 glyph_top/bottom
  • 背景 mode 色、文本众数色
  • 擦除蒙版（逐笔画膨胀，决定残墨）
关键发现：宽度分不出等级。样本里 25 张带徽章的图，mock_scale 认定成功 17 张，其中 15 张宽度都是 57px（用户等级 3~19 各不相同）—— 而口径 C2 现在只比「宽度同档 ±3」，等于只验证了「都有一颗丸」，等级对不对它看不出来。livepipe 的 badge_text 是目前唯一能落到「等级相同」的信号。 但等级对成品没有像素影响（贴的是目标自己的丸，覆盖写）⇒ C 买的是配对语义与审计，不是像素。所以它要做，但必须带三级降级链（等级相同 > 等级未知退回宽度 > 明确不同排除），见 §3.2。

单张量测的耗时构成（73 张实测，720×1600）

解码 7.3ms（44%） 定位 7.2ms（43%） 徽章 2.2ms（13%）

换算：2,178 张 × 16.7ms ≈ 36s CPU（8 workers 理想 4.5s，实际受磁盘与进程开销限制）。 ⚠️ 解码占 44% —— 这也是缓存的真正收益面：命中即不读图，而不是省那 7ms 的计算。

3 · 执行顺序（七步，livepipe 排在前置）

顺序由依赖定，不由工时定：C 等着 livepipe 的等级，B/D 的收益等着 C 定下候选池，E 要把 plan 绑死；而 0 给出后面所有收益的分母，所以仍然第一个做。

两个判据（C 的三级链、livepipe 的加法前置）的完整推理与数据见 docs/决策说明-档C与manifest.html；每一步怎么评测（指标、噪声底、A/B 协议）见 docs/评测方案.html；改哪里、按什么顺序改见 docs/评测落地计划.html；本页只排执行顺序、依赖与验收。

livepipe 侧验收：关 ⇒ manifest 与今天逐字节相同；开 ⇒ diff 只允许 schema_version 与新增的 row 键；row.roi 与图 roi 100% 相同；badge_level 要么是 1~3 位数字、要么是空串。

3.2 档 C：三级降级链（不是「只留同等级」）

纯「等级相同」会把 32% 的目标配空（中位候选 24 → 1.5）—— 那是硬损失。三级链用「未知」把池子补回来，只砍「明确不同」：

层目标等级底图等级动作样本量级
1已知已知且相同首选中位 1.5 张
2已知未知（读不出 / 脏值 / 无读数）允许，退回宽度判据（现状口径）约 2/3 的图是「未知」
3已知已知且不同排除只砍明确不同
目标等级未知整条链退化为现状：只按宽度约 29%（14/48 个目标）

宽度闸（BADGE_W_TOL = 3）在每一层都仍然生效 —— 等级不是宽度的替代品，它只在「能判断」时加一层排序。

脏值闸（只降级，不排除）：同时满足才算「已知」—— ① badge_level 是 1~3 位数字；② 同一 rid 的多次读数全部一致（A 从 rows.jsonl 顺带拿到）；③ 与账号级 level 不冲突。任一条不满足 ⇒ 当「未知」走第 2 层。绝不能让一次 OCR 误读变成「等级不同」的排除。
A/B 对照项（同语料 · 同 seed · C 关/开各跑一遍）阈值为什么是这一条
配空率（0 候选的目标占比）≤ 基线 + 1pp，且 ≤ 2%三级链的全部意义；超标就停下来重新拍板（加第 4 层或回滚），不静默放宽
等级一致配对占比（双方已知）≥ 70%证明第 1 层确实在起作用，而不是被第 2 层吞掉
出片张数（P3/P4）≥ 基线C 只该改配对，不该改产量
expand_plan.json 差异面仅配对字段其余字段逐字段相同（seed 固定 20261010）

诚实说清楚：等级对成品没有像素影响（贴的是目标自己的丸，覆盖写）。C 买的是配对语义可控、可审计，不是更好看 —— 所以它必须配一条不亏产量的降级链，收益也只能记在「对账/语义」栏，不能记进「省时间」栏。

3.3 B / D / E 的依赖补丁

  • B 的 key 不放 lp_level：缓存存的是像素量测（slot_width / glyph_height / badge_rect / 背景色），等级只影响配对、不影响量测。把等级放进 key，C 一调参数整批缓存就作废 —— 方向是反的。key = rel + t + panel + (roi_inset, roi_vinset, profile, 代码版本) + size/mtime。B 的收益也要用 C 之后的分母：缓存省的是「重复量测的次数」，而 plan/run 覆盖的图数会随配空率变 —— 拿 C 之前的数报会偏高。
  • D 的收益等 C 的数据：两遍量测省掉的是「落选图」的徽章量测与列扫描，而落选面由配对规则决定。C 把候选池从「宽度同档」换成「三级链」⇒ 必须先跑 C 的 A/B，拿到配空率与各层命中数，再估 D 能省多少。顺序反了就是拿旧分母报收益。
  • E 加 plan 指纹：expand_plan.json 顶部写 plan_fingerprint（source / ratio / min_images / base_cap / per_target_per_base / seed / 口径常量 / C 规则版本与参数 / livepipe join 摘要 的 sha256），run report 每张记指纹；续跑只复用指纹相同且 扩展N.jpg 存在的 job。没有它，C 改了配对之后旧报告里的 ok 会被当成新结果复用 —— 正是 bug-300 那种「账和片子不是同一把尺子」。

4 · 守口径与护栏

⚠ 边界：① render_one → process_image 出片路径一字不动（2026-10-11 定案「全盘照上游」，§22）；② 不改 BADGE_* / JOIN_GAP_* / ROI_* 任何常量（§18.3 内缩 5px 是逐张回放标定出来的）； ③ livepipe 侧只做加法 —— 新键 + 新块 + schema 版本，默认关；旧产物逐字节不变，不改任何既有字段的语义； ④ mock_scale 不写 livepipe 目录 —— 只读；join 结果落自己的 livepipe_join.json。
被同型改动坑过的两次：
① bug-300：规划与出片用了不同的框/内缩量 —— 「账上量到的」与「实际擦写的」不是同一处 ⇒ 缓存 key 必须把 roi_inset / roi_vinset / profile 绑死；
② bug-284：ASCII 目录只量第一张，第一张恰好没徽章 ⇒ 整户误杀 ⇒ 两遍量测只许延后徽章，不许跳过（自己的图仍每张都量）。
