1 · 为什么先补账

评测方案里有两个洞，不补就量不出数：

洞 1 · C 算不出配空率。cmd_plan 里构造的 short（0 候选名单）只打印、不落盘（expand_produce.py:1500-1502），users[] 也没有候选池大小；而 allocate() 的 skip_stat 是按 path 记、只有两种原因，不是按目标记。R_blank 与三层命中数现在都算不出来。
洞 2 · B 的命中率分母会被做小。只拿 plan 的 2,178 次当分母，会把 run 的 590 次重复定位漏掉，命中率直接翻倍。分母必须是「plan + run 的重复定位 + 重跑」，并且两臂都从空缓存起步。

两条都指向同一件事：埋点要一次做够。分四次改 schema（B 一次、C 一次、D 一次、E 一次），就得跑四遍基线，四份账还互相对不上。所以 P0 一次性把 B/C/D/E 需要的计数与轨迹都埋好，后面每一步只开开关、只读字段。

3 · 评测台 eval/bench.py

bench 不 import 产品代码、不复制判据，只通过命令行跑产品、读产物、对拍 md5。这样产品怎么改，评测台都不用跟着改。

python3 eval/bench.py snapshot --corpus "$SRC" --into "$EVAL/corpus"
python3 eval/bench.py pair     --snapshot "$EVAL/corpus" --tag-a A --tag-b B --repeat 3 \
                               --a-arm eval/arms/A-baseline.json \
                               --b-arm eval/arms/B-cache-warm.json --eval-root "$EVAL"
python3 eval/bench.py compare  --a "$EVAL/runs/A" --b "$EVAL/runs/B" \
                               --thresholds eval/thresholds.json \
                               --baseline "$EVAL/baseline.json" \
                               --out "$EVAL/compare-A-B.json"
python3 eval/bench.py baseline --run "$EVAL/runs/A" --run "$EVAL/runs/A2" \
                               --eval-root "$EVAL" --scope full-1478 --out "$EVAL/baseline.json"
python3 eval/bench.py crash    --snapshot "$EVAL/corpus" --eval-root "$EVAL" \
                               --arm eval/arms/A-baseline.json --kill-after 20 \
                               --out "$EVAL/eval-E-resume.json"
python3 eval/bench.py verify   --corpus "$SRC" --md5 "$EVAL/corpus.md5"

crash 是 E 档的验收：完整跑一遍当参照 → 起 --mode run 等 journal 攒到 --kill-after 张 → SIGKILL 整个进程组 → 同 out --resume（要求复用 > 0、md5 差 0）→ 换 seed 再续跑（要求复用 0、stale_fingerprint > 0）。

pair 就是协议里的「A/B/A/B/A/B」：奇数轮 A→B、偶数轮 B→A，两臂的 rep<i> 共用轮次号；同配置两臂即 placebo。baseline 把同配置的若干 --run 并起来算中位数 / p95 / CV，写出冻结的噪声带（noise.band_pct）；compare --baseline 优先用它（并要求语料指纹一致），没给才退回本臂 CV。它只存输出树的摘要，不存逐文件 md5 表 —— 那张表的键是用户目录名。

臂与阈值都是文件，不是代码里的常数 —— 改阈值必须改文件、进 diff：

// eval/arms/A-join.json（A 档：只在 plan 时开）
{ "name": "A-join", "workers": 8, "seed": 20261010, "cache": "cold",
  "plan_flags": ["--livepipe-join"], "run_flags": [] }

// eval/thresholds.json
{
  "T_total":  { "kind": "time",  "min_delta_over_noise": 2 },
  "R_blank":  { "kind": "blank", "max_over_baseline_pp": 1, "abs_max": 2 },
  "R_lvl":    { "kind": "ratio", "min": 0.70 },
  "N_out":    { "kind": "count", "min": "baseline" },
  "E_out":    { "kind": "count", "max": 0 },
  "J_join":   { "kind": "ratio", "min": 1.0 },
  "J_conflict": { "kind": "count", "max": 0 }
}

compare 的输出就是评测方案 §5 的 eval_metrics.json：两臂的中位数、噪声带、Δ/Δ%、每条通过线的结论。缺指标写 null 并判 inconclusive，绝不拿 0 顶替。

退出码含义
0全部通过线通过
3有指标回退（超出阈值），报告照写
4四指纹不一致 / 缺失 ⇒ 两臂不可比
5原件被改动（md5 清单对不上）⇒ 立即停
6指标缺失 ⇒ inconclusive，不算通过

产品的退出码 3（缺口 >5%）不算评测失败：那一步在 report / reconcile 写完之后才发生，产物是全的 ⇒ bench 照跑照记（summary.json 的 rc_values），只有其他非 0 码才当崩溃。噪声底按评测方案 §4 的 CV = (max−min)/median 算，不是 stdev/mean —— 后者对 3 次重复只有前者约 0.4 倍，会把带内抖动判成收益。

6 · 风险与回滚

  • 埋点改变产物：计时和计数都不参与判据；但新增字段会改 plan/report 的字节。比产物、不比账本：扩展*.jpg 的 md5 是硬线，账本新增键列白名单。
  • 逐图 JSONL 太慢：2,178 行是小文件；缓冲后一次写，别每张 open/close。
  • schema 变更弄坏老读者：只增键、读者用 .get()；拿一份 schema 6 的旧 plan 跑一遍回归。
  • 配对轨迹泄隐私：expand_pairs.jsonl 含用户目录名，只落在本地 eval/ 与快照里，不进交付包、不进 git（写 .gitignore）。
  • C 的等级字段还是 null：bench 把 R_lvl 标 null/inconclusive，不许算成 0%；等 A/livepipe 接上再评。
回滚方式：P0 全部是新键/新文件，回滚 = 不读它们（老逻辑不看新键，产物不变）；bench 是独立脚本，删掉不影响产品。唯一不可回滚的是已经用新 schema 产出的 plan —— 但它能被老代码读（只多键），不需要回滚。
