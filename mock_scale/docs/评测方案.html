1 · 评测台：快照 → 两臂 → 指标 → 判定

评测不是「跑一遍看看快了多少」，而是对照实验：同一份快照上开/关各跑 3 遍，先量出这台机器的噪声底，再判断差值是不是真的。任何一步换了分母（快照、参数、缓存状态、机器），两边的数就不可比，报告整份作废。

一次评测的四个动作（左右两臂只差一个开关）

左边两臂必须来自同一份快照；右边判定只认预注册的指标。噪声底不是可选项 —— 没有它，任何 3% 的差都可以被说成「提升」。

1.1 怎么跑

# 0) 快照：评测只在副本上跑，原件一个字节都不动
EVAL=~/eval/2026-10-28-baseline
SNAP=$EVAL/corpus
rsync -a --exclude '扩展*' "$SRC/" "$SNAP/"
find "$SNAP" \( -name '*.jpg' -o -name '*.png' \) -print0 | sort -z | xargs -0 md5sum > "$EVAL/corpus.md5"

# 1) 两臂交错跑；每臂 3 遍；run 一律 --out（绝不给 --yes）
for i in 1 2 3; do
  rm -f expand/measure_cache.json            # 冷缓存：两臂同一起点
  /usr/bin/time -f "A$i plan %e s" python3 expand/expand_produce.py \
      --mode plan --source "$SNAP" --seed 20261010 --workers 8
  /usr/bin/time -f "A$i run  %e s" python3 expand/expand_produce.py \
      --mode run  --source "$SNAP" --out "$EVAL/A$i"
done

臂 B 只把 --mode run 换成开开关的版本（如 --cache），其余参数逐字相同；两臂的输出目录分开，产物对拍时才有得比。

安全红线：评测永远不给 --yes、永远带 --out。语料是真实用户截图，就地写回会覆写语料；快照用 rsync 复制，连 expand_plan.json 也只写进快照。评测前后对原件跑一次 md5 清单，必须逐条相同。

2 · 指标字典（先定义，再跑）

指标分两类：时间栏（墙钟、分项、命中）与语义栏（配空率、等级一致率、产物差异）。两栏分开记，任何一步都不许把语义收益折成秒。

指标定义 / 公式取数方向
T_plan / T_run一次完整运行的墙钟（含进程启动、读图 IO、落盘）；每臂 3 次取中位数，同时记 p95/usr/bin/time -f %e 或外层 perf_counter↓
T_stage单图分项：量测 decode / locate / badge；出片 render / check / save。求和 + 分位0 步打点，逐图写进 plan meta 与 run report↓
N_measure提交给 measure_all 的图数（真值 = len(items)，含 ASCII 补量）plan 打印「量了 N 张」→ 落 meta=
N_jobs / N_out计划 job 数 / status=="ok" 数expand_run_report.json≥
E_out全部 扩展*.jpg 的 (rel, md5) 集合差异数评测脚本对拍两臂输出树0
H_cache命中次数 ÷ 需要量测的次数（底图量测 + 字号拟合扫描；plan + run 的重复定位 + 重跑）缓存计数器（B 步加）↑
R_blank0 候选的目标数 ÷ 需补图的目标数plan users[].short_reason / short[]（0 步已落地）≤ 基线 +1pp
R_lvl双方已知且等级相同的配对 ÷ 双方已知的配对expand_pairs.jsonl（0 步已落地；等级字段 C 之前为 null）≥ 70%
F四指纹：语料 md5 清单、plan 指纹、git rev-parse HEAD（含 dirty）、环境（workers / 缓存状态 / CPU）评测脚本=

16.7 ms 的单图分项（decode 7.3 / locate 7.2 / badge 2.2）来自 73 张样本，只用于讲机制；真实语料上的分项由 0 步量出来。判定一律用墙钟，分项只用来定位是哪一段变了。

3.1 B：命中率的分母要先说死

同一个 H_cache，分母取「只算 plan 的 2,178 次」还是「plan + run 的 590 次重复定位 + 重跑」，能差出一倍。分母定成「所有需要量测的次数」，并在报告里写清：

# 分母（一次完整评测）
N_need = N_measure(plan, 2,178) + N_fit(字号拟合扫描) + N_relocate(run, 590) + N_rerun(重跑时需要量的)
H_cache = (cache_hit + fit_hit) / N_need

为什么把字号拟合算进量测：`fit_font_size_for` 是「二分字号 → 真画一遍字 → 量墨高」， 每次选材对每个（目标名字 × 底图字高）都做一次 —— sample-73 上 1064 次调用 / 7039 次 measure_ink，占 plan 墙钟的大头（~3.6s/4.4s）。它同样是只由像素决定的纯函数 （文字 + 字高 + 字体文件），不含量级/配对，正是 B 要缓存的东西。不把它算进去，B 的「机制」 与「时间」会脱节：底图量测全命中、plan 墙钟却几乎不动。

另一个自欺点：热缓存那一臂如果再跑一遍，命中率天然更高。两臂都必须从空缓存起步，热臂只允许在同一轮内复用自己写下的缓存（评测台的做法：删缓存 → 不计时地完整跑一遍预热 → 计时跑第二遍）。收益算法：

ΔT_B = T_cold − T_warm          # 中位数之差，必须 > 噪声底
省时上界 = 命中次数 × 单次量测（底图 decode+locate+badge / 一次字号二分扫描）

单图量测 ≈ 16.7 ms（样本）；真实值以 0 步分项为准。命中一次省的是整条量测，不是只省解码。

3.2 C：先把账补齐，再谈 A/B

这段是 C 的前置条件，已在 0 步（2026-10-27）补齐。之前「0 候选」的名单 short 只打印、不落盘（expand_produce.py 里构造完 short 就丢了），plan 的 users[] 也没有候选池大小 —— 那样跑 C 的 A/B，R_blank 与三层命中数都算不出来。补的就是这两样：

要补的账写什么为什么必须
plan users[] 加 pool / short 每个目标：过完全部闸后的候选数；配不够的原因（无候选 / 无贴图源 / 结构坏） 配空率的分母与分子都在这；只从 expand_reconcile.csv 的「缺口」反推会把「没候选」与「出片失败」混成一种
新增 expand_pairs.jsonl 每次配对一行：dir / base / base_user / tier / t_level / b_level / w_t；被第 3 层排除的也记一行 tier="excluded" R_lvl、三层命中数、审计「为什么换了这张底图」都靠它；事后从产物反推不回来
通过线的写法要小心：「R_blank ≤ 基线 +1pp，且 ≤2%」。如果基线本身已经 >1%，第二条会自相矛盾（必失败）。所以先量基线；若基线 >1%，绝对上限要重新拍板，不能静默放宽。

3.3 D 的收益必须等 C 的候选池

D 省的是「落选图」的徽章量测与列扫描，而落选面由配对规则决定。C 把候选池从「宽度同档」换成三级链之后，落选图的数量与分布都会变 —— 先跑 C 的 A/B 拿到 R_blank 与各层命中数，再估 D。顺序反了，就是拿旧分母报收益。

D 的两个计数器：N_badge（调 badge_rect_of 的次数）已随 0 步落地（plan meta.counters.badge_calls）；N_scan_px（列扫描的像素列数）要改共享的 core/inkmask.py，等 D 开工再加 —— 现在 report 里先写 0，表示「字段在、还没接」，不是「扫了 0 列」。

3.4 E：崩溃测试要真的崩

  1. 在 K=200 个 job 处 kill -9（不是正常退出）；
  2. 重跑同一命令，读 report 的 resume 段：复用数 > 0、重做的 job 只应是「未完成的尾部」；
  3. 对拍产物：复用路径与全量路径的 md5 逐张相同；
  4. 改一个 plan 指纹字段（如 seed）再续跑：必须全量重跑，复用数 = 0。

4 · 噪声底与判定

先有带子，才有「提升」

带子由 placebo 跑出来（同配置两次的差）。带内的 3% 不是提升，是抖动；把它写成收益，下一步就会按错的方向继续优化。

规则怎么做为什么
先跑 placebo同配置连跑 3 次，取 CV = (max−min) / median；CV > 5% 先降噪（固定 workers、别的同时任务停掉）没有带子，任何差值都能自圆其说
交错跑A/B/A/B/A/B，不是 A×3 再 B×3热漂移、系统缓存会让后跑的占便宜
判定式ΔT > 2 × CV × median（或 > placebo 的 p95）才算收益阈值预注册，跑完不许改
报比值报告里同时给 Δ（秒）与 Δ%；换机器只看 Δ%绝对秒数不可跨机器比较

落地时：bench baseline 把同配置的多遍合成 eval/baseline.json（中位数 / p95 / CV / 噪声带），bench compare --baseline 用它的 band_pct 当门槛，并要求两臂语料指纹与基线一致；没给基线才退回本臂 CV。仓库里当前那份是 scope: sample-73（12 遍交错，CV 3.73% ⇒ 带 ±7.47%），不是生产噪声带。

5 · 报告长什么样

每次运行落一份 eval/<date>-<tag>.json（在语料之外），字段固定；缺指纹的报告不参与比较。

{
  "schema_version": 1,
  "tag": "B-warm-3",
  "fingerprint": {
    "corpus_sha256": "…",          ← corpus.md5 排序后再 sha256
    "plan_sha256": "…",            ← 与 E 的 plan 指纹同一算法
    "code": "…",                   ← git rev-parse HEAD + dirty
    "env": "workers=8 · cache=warm · run=3 · cpu=…"
  },
  "wall_s":  { "plan": …, "run": …, "total": … },
  "stage_ms":{ "decode": …, "locate": …, "badge": …,
               "render": …, "check": …, "save": … },
  "counts":  { "measure": 2178, "jobs": 590, "out": …,
               "cache_hit": …, "blank_targets": … },
  "quality": { "blank_rate": …, "level_consistent": …,
               "out_md5_diff": 0 },
  "verdict": { "metric": "T_total", "delta_pct": …, "noise_pct": …,
               "pass": true }
}

示意的是字段结构，… 由每次运行写入实测值。counts.measure 与 counts.jobs 写的是本轮真值，不是常量 —— 口径改了它们就该变。

6 · 反模式（照到一个，这份评测就不算数）

  • 拿旧分母报 D：C 已经改过候选池，D 还用 C 之前的落选图数。
  • 一臂冷、一臂热：B 的两臂缓存状态不同，命中率是假的。
  • 只报总时长：分不清是哪一段变了，也没法排除「IO 抖动」。分项和墙钟必须同时有。
  • 用样本推全量：拿 73 张样本的 16.7 ms 去乘 2,178，报「省了 36 秒」—— 样本只用来讲机制。
  • 把语义收益折成秒：C 的像素收益是 0，它买的是「配对可控、可审计」。
  • 在原件上跑：没有快照、没有 --out，一次误操作就把语料改了。
