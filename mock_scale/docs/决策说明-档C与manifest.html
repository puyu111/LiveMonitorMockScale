1 · 档 C：把「宽度同档」改成「等级相同」

1.1 现在的判据其实在管什么

口径 C2「底图徽章与目标徽章同档（宽度 ±3px）」服务的不是等级语义，是贴图能不能盖住：paste_badge 会把目标用户自己那颗丸覆盖到底图的徽章位上；尺寸差超过 ±3px 就不硬贴（会露边）。所以判据量的是「丸的几何档位」，不是「丸里写几级」。C 要改的就是这一层：宽度闸保留，等级只加一层排序与排除（见 1.3）。

贴图机制：成品上的等级来自目标，与底图无关

依据：paste_badge() —— 「把目标用户自己的徽章贴图覆盖到底图的徽章位上；尺寸差太多不硬贴（会露边）」。同宽时零平移。

1.2 纯同等级（不做降级）的代价：三分之一的目标直接配空

一个目标能借到的底图数（样本 34 个有等级的目标，中位）

现状：宽度同档 纯同等级（未降级）

样本 73 张里只有 25 张读得到干净等级（34%）；48 个用户里 34 个有等级，其中 11 个（32%）找不到任何同等级的底图。这张图画的是纯「只留同等级」的代价：这一成目标候选数归零，等于按口径④不出片 —— 这正是下面三级链要解决的问题，不是 C 该不该做的理由。

⚠ 还有一个隐含前提：badge_text 是 OCR 读数，样本里 25/25 干净，但全量 rows 里能看到 14冷***、我***送出玫瑰 这类把昵称/正文咬进来的脏值（约 7%）。真拿它当判据，必须先过「纯数字」闸，否则会把「读错」当成「等级不同」。

1.3 三级降级链：把配空补回来

纯「等级相同」把 32% 的目标配空，是因为「读不到等级」被当成了「不是同一个等级」。三级链把它拆开 —— 未知不是不同：

层目标等级底图等级动作样本量级
1已知已知且相同首选中位 1.5 张
2已知未知（读不出 / 脏值 / 无读数）允许，退回宽度判据（现状口径）约 2/3 的图是「未知」
3已知已知且不同排除只砍明确不同
目标等级未知整条链退化为现状：只按宽度约 29%（14/48 个目标）

宽度闸（BADGE_W_TOL = 3）在每一层都仍然生效 —— 等级不是宽度的替代品，它只在「能判断」时多一层排序。第 2 层是关键：读不到等级的药丸在两版里都占多数，把它们当「不同」排除，等于把 1.2 的损失重新引进来。

1.4 脏值闸与 A/B 阈值

脏值闸（只降级，不排除）：同时满足才算「已知」—— ① badge_level 是 1~3 位数字；② 同一 rid 的多次读数全部一致（A 从 rows.jsonl 顺带拿到）；③ 与账号级 level 不冲突。任一条不满足 ⇒ 当「未知」走第 2 层。绝不能让一次 OCR 误读变成「等级不同」的排除 —— 那会把损失做得更隐蔽。
A/B 对照项（同语料 · 同 seed · C 关/开各跑一遍）阈值为什么是这一条
配空率（0 候选的目标占比）≤ 基线 + 1pp，且 ≤ 2%三级链的全部意义；超标就停下来重新拍板（加第 4 层或回滚），不静默放宽
等级一致配对占比（双方已知）≥ 70%证明第 1 层确实在起作用，而不是被第 2 层吞掉
出片张数（P3/P4）≥ 基线C 只该改配对，不该改产量
expand_plan.json 差异面仅配对字段其余字段逐字段相同（seed 固定 20261010）

1.5 建议

做 C，按三级链落地。① 等级只做排序与排除，不做硬过滤；② 脏值只降级、不排除；③ 先跑 A/B，三条阈值全过才上线；④ 报告里同时记「各层命中数 / 配空率 / 等级一致率」，让下一轮能直接看出链子有没有塌。 仍然要诚实：像素收益为 0（贴的是目标自己的丸，覆盖写），C 买的是配对语义可控、可审计；所以它不值得为它牺牲产量 —— 三级链就是这条边界。

2.2 改法：三个件，全是加法

件写什么为什么这么写
schema_versionio.py: SCHEMA_VERSION 2 → 3；只有写了 row 块才写 3，关掉时仍是 2版本是消费者判断「有没有 row 块」的唯一开关；不写 3 的产物与今天逐字节相同
可选 row 块--row-geometry（默认 off）；开时 images[] 每条多一个 row：box / text_box / colon_box / badge_box / badge_left / badge_text / badge_level / x_text / x_right / rid数据源是段目录的 comments.jsonl，export 按 roi join 一次（73/73）；关时不改任何既有字段
badge_level 干净字段调现成的 account_id.badge_level()（NFKC + Unicode Nd，与账号身份同一条判据）；读不出写 ""脏值在源头清一次；下游各写一遍 isdigit 早晚不一致（现有 ~7% 脏值）

改动面就两个文件：tools/export_user_images/io.py（版本常量）与 tools/export_user_images/run.py（读段目录的 comments.jsonl、按 roi 建索引、给 images[] 挂 row）。不动 qualify、不动 users_qualified.jsonl 的 6 键投影 —— 那会让旧产物变字节。

一个纠正：上一版方案里我把 join 源写成 rows.jsonl（要按 t+panel 取行、按 y 区间判多行）——实测换成 comments.jsonl 按 roi 精确匹配 73/73，更简单也更硬。方案 A 的实现细节按这个改。

2.3 两仓库怎么解耦上线

阶段livepipemock_scale
① 先合入合 --row-geometry，默认关；跑回归证明旧产物逐字节不变不动。A 仍用 comments.jsonl 的 roi join（73/73）
② 重导语料加 --row-geometry 导出，manifest 升 v3不动。A 有 row 就用、没有就退 —— 不需要同一天发版
③ 收尾文档写明 v2 / v3 都能读报告里打「join 来源」列；row 覆盖 100% 后再删 join 推导的兜底
结论：改，但按「加法 + 默认关」改。它解的不是「join 能不能做」（已经 73/73），而是「join 在几个仓库各写一遍」—— 现在由 livepipe 写一次、下游读现成的；同时保留 comments.jsonl 这条不依赖新版本的退路。
