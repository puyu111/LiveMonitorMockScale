# mock_scale 技术说明

**把直播截图里标注框内的用户名换掉** —— 换完之后，标注框、冒号、右侧评论、徽章、
背景底色**一个像素都不许变**，而且「名字 ↔ 冒号 ↔ 正文」这三段的相对距离要保持原样。

本文说明这套东西**为什么这样做**：踩过的坑、量出来的数、以及结论**在什么条件下才成立**。
「规格 + 逐图验证记录」在 [`../README.md`](../README.md)，本文不重复那部分。

> 📁 **2026-10-27 合并后**：管线、工具与运行配置只有 **`core/` 一份**；`mock/`（假名字出假图）
> 与 `expand/`（给真实用户补图）两条线只保留各自的入口与本线资料，用 `sys.path` 指向 `core/`。
> 本文里引到的 `batch_run.py` / `inkmask.py` 这类**共用模块**，都在 `core/`。
> （旧 `test2` 路径与 `check_shared.py` 漂移守卫的去向见 [`工程结构.md`](工程结构.md)。）

```
一句话：把「擦字」从云端模型换成两件确定性的事 ——
        ① 用邻域插值把字抹掉（本地，0 元，0.72s/张）
        ② 用「搬原图像素」而不是「重画」来排布冒号与正文
        代价是适用范围窄：背景要近乎纯色，且用户名得是框内唯一的高饱和色文字。
```

## 1. 问题与背景

输入是抖音直播间的横版截图（2560×1520），每条评论一行，外面套一圈彩色描边（标注框），
框里是 `[用户名][：][评论正文]`。需求是**把用户名换成另一个名字，其余部分保持原样**。

原方案是四步流水线：

```
① HSV 提彩色标注框  →  ② 框内定位用户名 → 生成蒙版  →  ③ 云 API 擦字  →  ④ Pillow 写新名字
```

前三步都能跑通，**问题全部出在第 ③ 步**。第 ③ 步试过两条云路线，
两条都是花了真钱、拿真调用量出来的结论（不是文档推断、不是偏好）：

| 路线 | 实测结果 |
|---|---|
| `wanx2.1-imageedit`（带蒙版的局部重绘） | 14 张真调，**擦干净只有 3 张**；**4 张擦完字反而更多**（模型在蒙版区**凭空造字**，如 2569→2951 px）。同用户同几何的两张图，一张干净一张造字 ⇒ 判定为**模型端随机性**，不是提示词/对齐/合成的问题 |
| `qwen-image-edit-plus`（指令式、无蒙版） | **冒号丢**（9 次调用、三种措辞，没有一种能保住）；**样式随机**（新名字颜色在淡蓝/淡青之间跳）；**框内邻居被重画** —— 框内非用户名区域 **23.1% 的像素被改动、最大色阶差 246**（金色表情被搅乱、「奇瑞」两个字被抹掉） |

而本场景恰好是 inpainting 的**最简情形**：

* 背景是近乎纯色的暗色 UI 底 —— 实测众数色 `(37,37,49)`、标准差 ≈ 5；
* 用户名是**框内唯一的高饱和色**文字（饱和度 70~80，而正文白只有 4~6）。

这正好是传统确定性算法最擅长、并且**物理上不可能造字**的场合：插值只会复用邻域里
已经存在的像素，它没有「想象一个新笔画」的能力。

> 顺带做过一次取证：需求原文写的是 `qwen-image-plus`，而**该模型是纯文生图**
> （输入模态只有 Text），不接受图片输入 —— 照原文打过去返回
> `400 InvalidParameter`。用一个**只改模型名**的单变量对照（同样的 payload 打
> `qwen-image-edit-plus`）拿到 200 并返回可用图片，才把这条坐实。

## 2. 四条路线与选型

| | 路线 | 决定性证据 | 结论 |
|---|---|---|---|
| **A** | 云 API 蒙版重绘<br>`wanx2.1-imageedit` | 14 张里只擦干净 3 张；**4 张凭空造字** | ✗ 不可用 |
| **B** | 指令式编辑模型<br>`qwen-image-edit-plus` | 冒号必丢、样式随机、邻居被改 23.1% | ✗ 不可用 |
| **C** | **本地确定性 inpainting**<br>OpenCV `INPAINT_TELEA` / `ns` | 8/8 全清、蒙版外 **0** 像素改动、**0** 次造字 | ✓ **选它** |
| **D** | 直接填背景色（`flat`） | 背景平的地方可用，背景一有纹理就露补丁 | ○ 实现为对照（`--method flat`） |

C 相对 A/B 多出来的三条，**都不是「效果更好一点」，而是性质上的差别**：

1. **确定性** —— 同样的输入永远给同样的输出。A 路线的失败是随机的，意味着**无法
   通过重试收敛**，只能靠人逐张检查。
2. **局部性是构造保证，不是接口行为** —— 见 §3.2。A 路线「只有白区被重绘」是**接口承诺**，
   可以失效（23.1% 那个 bug 就是这么来的）；C 路线的「蒙版外逐像素不变」是**代码结构**决定的。
3. **没有尺寸下限** —— 云接口有 `≥512px` 硬约束，实测 295×47 的框必须先外扩裁剪再缩回，
   一来一回多一次重采样；本地路线直接在原分辨率上按蒙版擦。

代价是**适用面窄**，见 §5。

## 3. 管线：定位 → 擦除 → 排版

三段，全部本地，三个依赖（`numpy` / `opencv-python-headless` / `Pillow`）。

### 3.1 定位（`core/inkmask.py`）

在标注框里找出「用户名 + 冒号 + 正文」这条装配的几何，并产出擦除蒙版。

**① 内缩 + 按颜色削边。** 框坐标是**含彩色描边**的外框，先内缩 `BOX_INSET=6` px 把描边
排除掉。但**固定的内缩挡不住逐图变化的量**：描边的抗锯齿会往框内多糊 1~2px，而糊多少
逐图不同 —— 有一张图的描边一直糊到「框右缘 −7」列，正好落在 inset 之内，于是那一列被
当成正文墨迹、跟着尾巴一起被搬走，绿框内缘缺了 30 个像素。修法是内缩之后再**按颜色**削一刀
（`shave_frame`：最外一列若 ≥90% 像素「绿占优」就削掉）。**不能靠加大 inset 解决** ——
那是全局量，会把另一张图的字顶字底切掉。

**② 取背景众数色 → 量墨迹。** 与背景色的**最大通道差** > `BG_DIST_THRESH=45` 才算墨迹。
实测背景是 40~60 亮度、文字像素 200+，45 落在两者的巨大空隙里。

**③ 列投影切段。** 墨迹按列投影成若干个连通段。

> ⚠️ **按位置切分是错的**：正文里字与字之间有空隙，会被切成**多段** —— 实测有一张图的
> 正文就是 `[198-253] / [255-280] / [310-421]` 三段。当初按「最右段是正文」切，
> 8 张错 6 张：正文的前半截被当成名字擦掉了。

**④ 用核心色饱和度认名字**（本模块**最关键**的一条判据）。每个段取「最亮 25% 像素」的
中位色作为核心色，再算它的饱和度：

| 结构 | 核心色饱和度 | 段宽 |
|---|---|---|
| 徽章 | 55 ~ 60 | 66 ~ 76 |
| **用户名** | **70 ~ 80** | 26 ~ 28 |
| 冒号 | 31 ~ 42 | 4 ~ 5 |
| 正文（白） | 4 ~ 6 | 25 ~ 308 |

用户名与冒号之间是个**空档**，阈值 60 落在中间、两侧各留 10 以上余量。这是按**颜色**切，
不是按位置切 —— 正文再长再碎也不影响。

**⑤ 剥离徽章。** 等级徽章是个**实心药丸**，比汉字宽得多，且饱和度也接近阈值。判据是
「填充率」= 段内墨迹像素 / (段宽 × 框高)：实测徽章 `0.74`，而汉字 `0.37~0.49`、
冒号 `0.20`。阈值 `0.60` 落在徽章与**一切文字**之间，因为它是「实心图形 vs 笔画」的判据。

⚠️ **填充率只认「实心药丸」，认不出「空心图标 + 数字」那种徽章**（2026-09-30 补的第二条判据）：
抖音有一版等级徽章是空心的，实测 `宝宝不乖-3/1.jpg` 填充率 **0.48** —— 正落在汉字的
0.37~0.49 里，**分不开**。漏掉它的后果是三连：徽章被当成名字的**第一个段** ⇒ 槽位把徽章圈进去
（**194px**，真名字只有 112px）、字高取到徽章的 **32px**（真名字 28px）、`text_color` 从**蓝紫色**
的徽章上取（徽章像素 `(112,128,224)` vs 名字 `(160,208,224)`）⇒ 出图「**名字又大又白**」。

补的判据是**笔画粗细**：`cv2.distanceTransform` 的峰值 —— 徽章 **16.0**、名字段在 8 张
`BOX_TABLE` 上一律 **3.0~3.2**、冒号 2.0、正文 3.0，差 5 倍（阈值 `BADGE_STROKE_MAX=6.0`）。
两条附带约束：
① 两条判据都仍要**同时**满足宽度 ≥ `BADGE_MIN_WIDTH`(40)—— emoji 也是图形，但它只有 26~28px
宽，是**名字的一部分**，不能剔；② 笔画那条**只对「上下连成一条带」的段生效** —— 框跨两行时
徽章会和两行文字在**列**上连成一整段（实测 `魂殿抖音分殿殿主-5/2.jpg` 宽 236、行 3~99），
笔画峰值一样高，不加这道闸会把整段（**含名字**）当徽章剔掉（实测回归 3 张）。
全量 **36 张**受益，被丢的段笔画峰值**全是 16.0**；**定位 464 → 480**（后续两轮再抬到 **496**，见 §6）。

**⑥ 导出几何。** 名字的**槽位**（原名字的墨迹左右界）、冒号的行列范围、
**尾巴**（冒号 + 正文）的包围盒、**槽位余量**（正文右缘到框右界的距离）、
**字带**（上下界）、文字本色、背景色。

### 3.1.1 「上下」这一维：字带与行带（2026-09-30 规格）

列投影只管**左右**；「字有多高」「框里是不是装了两行」是**上下**这一维的事，
过去没量，两个缺陷都出在这里。现在按**行带**量（`inkmask.row_bands`）：把有墨迹的行按
「相邻两行的缝 ≤ `ROW_BAND_GAP_PX`」聚成带，返回 `[(top, bottom, 墨量)]`。

**① 字带（修 bug-166）。** 字高过去取墨迹蒙版的**极值行** —— 一列孤立杂点就能顶掉整个字高。
实测：`inset=6` 之后右框内缘仍残留 1 列抗锯齿杂点、底框内缘残留 50 列，
`glyph_top/bottom` 被钉到整个内缩框高 **84px**，而昵称本体只有 **~33px** ⇒ 字号按 84px
算成 **88px**（框高才 96）⇒ 新名字在垂直方向撑出框沿 2px，而批量照报「不越框」。
现在取**墨量最大的那条带**（缝 ≤ `GLYPH_ROW_GAP_PX=3`）。**兜底**：若这条带仍高于
「一行字」的上限（复用 `NAME_EMOJI_MAX_SEG_H=45`），说明带里混进了别的东西（头像、
礼物动画、两行被连起来），改用**本色墨迹**（chroma ≥ `USERNAME_SAT_MIN`）的那条带 ——
名字的笔画是够饱和的，混进来的图形通常不是。全量 650 张里 **24 张**的字高被修正，
`>45px` 的从 **10 张降到 1 张**。

**② 行带（修 bug-168）。** 框检测只要求「框内前景占比 ≤0.35」，两行评论之间的空隙让它过关
（实测框高 96 里装两行、单行字高只有 27~32 ⇒ 段高 51~103）。这类框**四道判据全绿**却把
两行一起擦掉 —— 因为四道判据判的都是**几何自不自洽**，没有一道问「框里有几行」。
现在：全框有**两条以上**「≥ `ROW_BAND_MIN_ROWS=8` 行」的行带 ⇒ 判为跨行，本次出片
**只保留与名字重叠最多的那一条带** —— 擦除蒙版的**行**、尾巴块的**行范围**、冒号的行范围
全部夹进它，带外一概不动。上报在 `EraseRegion.multi_line` / `line_band`、
`rows.csv` 的 `multi_line` 列、报告末尾单列一行。全量命中 **10 张**；
**独立脚本复量：距行带 >3px 的改动 0 像素**（那 3px 是既有的蒙版膨胀环）。

⚠️ **两条与「量」有关的教训**（都踩过）：
① 字带/行带这种判据**只能量、不能推** —— 「蒙版外 0 改动」不等于「框外 0 改动」，
前者参照 `erase_box`，而 `erase_box` 由**可能被撑大的字形包围盒**推出；
② 同一个物理量**不能有两把尺子**：`join_gap` 原本按**列段边界**推
（`colon_span[0] - slot[1] - 1`），而 `gap_now` 在结果图上**按墨迹**量 —— 行带一切进来，
两行框里同一列由第二行提供的「参照」没了，3 张图当场报 `GAP_BAD`（bug-169）。
现在 `join_gap` 与 `gap_now` **同一把尺子**：同一个行窗口里、名字右缘之后的第一条墨迹列。

**⑦ 顺手报一句「名字段里有没有 emoji」**（`EraseRegion.name_emoji` / `has_emoji`，2026-09-29）。
**定位这一步不据此改变行为** —— 它只管把名字的几何圈出来。按 2026-09-30 的规格
（「含有表情也跳过」），批量流程据此**跳过整张图**（跳过的不计入任何数量、只留绝对路径），
单张模式只在日志里警告一句。判据与标定见 §6。

### 3.2 擦除（`core/inpaint_local.py`）

`cv2.inpaint` + `INPAINT_TELEA`，蒙版 = 名字笔画（含冒号）膨胀 3px（汉字边缘有 1~2px
抗锯齿过渡带，不扩进去会留下淡淡字影）。两个步骤是**必须**的，都是被 bug 教出来的：

**① 洗源（`clean_sources`）。** Telea 的取样半径会伸进 5px 厚的彩色描边里 —— 有一张图
字形下缘几乎贴边，于是**Telea 把绿色抹进了填充区**。修法：在工作副本里把「蒙版半径内的
非背景像素」先刷成背景色，让 Telea 只取到干净背景。⚠️ 这个 bug **指标抓不到**
（残余墨量、蒙版外改动都是好的），是**肉眼看对比图**看出来的。

**② 只贴蒙版内。**

```python
out = img.copy()
out[inside] = filled[inside]     # 只有蒙版内用插值结果
```

这一行把「蒙版外逐像素不变」从**事后断言**升级成**构造保证** —— 不是「我们检查过没变」，
而是**代码结构上不可能变**。§6 的批量跑里这一项 650 张全为 0，靠的就是它。

### 3.3 排版（`core/draw_text.py`）

规格是四句话叠出来的：

1. 冒号前是要修改的；冒号及其后不修改；
2. 短了用无字的部分填充，长了截取；
3. **冒号距离名字的距离不变**；
4. **正文也是相对距离不变，整体是否超过框，是则截断**。

> **后续补充（2026-09-29）**：
> 5. 「拼接的时候，不管正文还是用户名都不要表情」⇒ 新写的文本剔掉 emoji；
> 6. 「总体长度不够，生成更长的用户名，保持总体长度不变」⇒ 名字比槽位窄时**随机补字补满**
>    （第 2 句「短了用无字的部分填充」在「短」这一支上被它取代，旧做法可用 `--no-fill` 复现）。

第 3 句只说「冒号跟着名字走」，第 4 句才把模型补完整：`[名字][间距][：][间距][正文]`
是**一整块刚体**，一起平移 `位移 = 新名字墨迹宽 − 槽位宽`。于是：

* 名字**短**了 ⇒ **随机补字补满槽位**（`fill_to_slot`），于是位移 ≈ 0、尾巴几乎不动，
  8 张实测 `|名字宽 − 槽位宽| ≤ 2px`。旧做法（尾巴左移、右边填背景色）被规格取代；
* 名字**长**了 ⇒ 整条尾巴右移，吃掉框内余量；
* 余量吃光还放不下 ⇒ **从右往左截断**新名字（`--fit clip`，默认）。

**截断预算的边界因此不是「原名字的宽度」而是「框」**：
`预算 = 槽位宽 + 尾巴能让出的余量`，而余量 = 正文右缘到框右界的距离 − 安全边距。
实测 8 张图的余量差了 90px（0 ~ 92px），所以「`SuperUser` 放不放得下」逐图不同。

实现是**三段有序流水线**，顺序不能反：

```
plan_name    只算不画：去 emoji、定字号（对真实字体二分搜索墨迹高度）、按预算截字、
             名字比槽位窄时随机补满槽位、算出位移
shift_tail   把原图的「冒号 + 正文」像素整块搬到新位置，原位填背景色
render_name  最后写名字（Pillow）
```

### 3.4 为什么是「搬」而不是「画」

这是整份实现里最反直觉、也最关键的一条：**能搬原图像素就绝不重画。**

起因是一个很朴素的观察：用 Pillow 重画冒号，画出来的墨迹**宽 6px，而原文是 4px** ——
多出来的 2px 漏到了冒号右边，肉眼一看就是「冒号变粗了、位置怪」。字体再换、字号再调，
都不可能让 Pillow 的字形和原截图里**渲染引擎**的字形逐像素对齐。

所以尾巴（冒号 + 正文）**一个笔画都不重画**：把原图那块矩形整块复制到新位置。
字形天然一致、抗锯齿天然一致、正文里的每个字天然一致 —— 因为它们本来就是同一批像素。

这条承诺是可验证的，判据在 §4：把原图那块按位移取出来，与结果图对应位置**逐像素相同**。

**由此推出的三条连带结论**（每一条都对应一个真踩过的 bug）：

| 结论 | 踩的坑 |
|---|---|
| 搬尾巴必须在**写名字之前** | 先写字再搬尾巴时，为了「保护名字」把补丁左缘钳在名字右边，新名字一旦长过冒号原列，**冒号根本没被复制、直接被填成了背景**（结果图里冒号偏了 51px）。正解不是缩小范围，是**换顺序** |
| 搬运矩形的**四边都要钳进可动区** | 多搬的 2px 安全边距伸出内缩框后，把描边的抗锯齿边缘**拖走了**（4 张图被啃掉 124~549px 绿描边） |
| 安全边距要**同时**计进预算 | 否则预算算的是「刚好顶到框」，实际会用掉边距，间距从 5px 变成 6px |

## 4. 判据体系：为什么不能靠推理

每一条规格承诺都配一条**在结果图上重量**的判据。**不接受「按构造它应该是对的」** ——
抗锯齿、阈值、蒙版残留、绘制顺序都可能让「应该」落空。

**三条硬指标**（擦除）：

* `墨迹清除率` —— 擦完、**写字之前**量（写在最终图上量会把新名字算成残余，曾经报出
  「1326 → 1497 越擦越多」的假象）；
* `蒙版外改动` —— 必须恒为 0；
* `耗时 / 成本`。

**七项规格判据**（排版，全部在结果图上）：

| # | 判据 | 怎么量 |
|---|---|---|
| ① | 名字 ↔ 冒号的距离 | 从名字右缘往右找第一个墨迹列，必须等于原图的 `join_gap` |
| ② | 尾块是**原图像素** | 原图那块矩形 vs 结果图平移后的同一块矩形，逐像素比 |
| ③ | 冒号 ↔ 正文、正文各段之间 | 两边重新切列段，**段宽列表**与**段间距列表**都必须相等 |
| ④ | 腾出去的空隙 | 必须是纯背景，一点墨迹都不许剩（补满槽位后位移多为 0~±2px，这个区间常常为空，空区间自然成立；它现在守的是「万一没补满」） |
| ⑤ | 绿描边 | 原图里明确是绿的像素，**一个都不能变** |
| ⑥ | 框右界之外 | 零改动（这是「整体超过框就截断」的实测口径） |
| ⑦ | 内缩框上下之外 | 零改动 |

⚠️ **② 说的是「搬过去的那块是不是原图」，不是「原地搬干净了没有」。** 尾巴墨迹**探出标注框**时
（emoji 比正文高，或正文行本身比 `manifest.roi` 高），旧实现只搬框内那截 —— 探出的半截
**留在原地**，而 ② 照样全绿。2026-10-11 用户报的「移动正文，没有完全移动」正是这条缝。
现在多了一条**只报不判**的量：`tail_leftover_px` / `tail_clean`（见
[`../expand/扩展张数.md`](../expand/扩展张数.md) §25.1 量测 / §25.6 三条外壳上的落地）。

⚠️ **⑥ 只管右界。** 判据名字叫「不越框」，量的是**框右界那条竖线之外** ——
左/上没有对应的内建判据（左界本来就不会被越过：装配左对齐在名字槽位上）。
上下自 2026-09-30 起由**定位的行带**按构造守住（改动被夹在名字那一行的上下界内，
见 §3.1.1）；判据 ⑦ 是它在 8 张上的独立复核。
**这条口径已经漏过一次**：`A携酒话清风D疗-5/1.jpg` 的 `short` 档在绿框上沿外 2px 改了
54 个像素，批量照报 `box_ok`（bug-166，**已修**，见 §3.1.1）。教训留着：**报「零违规」之前，
先读判据的实现、确认它覆盖的是哪几条边。**

其中 ① ② ⑥ 已经**内建进主管线**，每次跑都在结果上量并汇总进日志
（`冒号距名字 ✓ / 尾块差 0px ✓ / 装配右缘 … 距框 Npx ✓`）；③④⑤⑦ 只在独立校验脚本里，
适合改动后回归。批量脚本 `core/batch_run.py` 把 ①②⑥ 提升成**每张图 × 每个探针**的判据，
所以 §6 里那 1488 次「零违规」就是这三条的统计。

> ⚠️ **判据本身出过四次假阴性**，全都不是代码错：把「绿描边」判成「与某个绿色基准的
> 最大通道差 <90」会误抓灰字；「腾空区」在名字变宽时算错了区间（那段被新名字盖住了）；
> 「框内边缘」把内缩框的第一行也框进去（那一行本就在可动区内、改了是合法的）；
> 用「最右墨迹列 < 框右界」当越框判据会被框外的绿描边顶掉（8/8 全部误报）。
> **报 ✗ 之前，先确认判据说的是你要验的那件事。**

## 5. 边界：什么时候不成立

**这套东西不是「擦字方案」，是「在这个语料上成立的擦字方案」。** 换语料前先读这五条：

1. **依赖「用户名是框内唯一的高饱和色文字」。** 昵称若本身不饱和（白/灰）、或者正文比昵称
   更亮，`USERNAME_SAT_MIN=60` 这条判据就不成立，定位会失败或**静默量错对象**
   （把正文白当成用户名 ⇒ 擦掉评论、留下用户名）。
   **昵称里带 emoji 也会破功** —— emoji 是实心团块，会被「填充率 ≥0.60 判徽章」的规则
   当成徽章剔掉，剩下的文字段拼不出结构。§6 实测：这类占定位失败的 **54.9%**。
   ⚠️ **这一类和「跳过」是两回事**：跳过判据是「昵称串只有 ASCII」（不读图）与
   「已定位到的名字段里有 emoji」两条，而这里的 emoji 在名字聚类**之前**就被当徽章剔了 ——
   名字压根没定位到，两条判据都够不着。所以这一类只能以「定位失败」的形态出现。
2. **依赖「背景近乎纯色」。** 本语料 std ≈ 5。背景一有渐变、纹理，或者评论压在图片/视频上，
   `flat` 会露补丁、Telea 会糊 —— 那种场合才轮到 inpainting 模型上场。
3. **样本代表性。** 最初那 8 张图全部来自**同一个用户目录**（同一版式的 8 次重复），
   不等于 8 个独立样本。§6 就是为这一条做的。
4. **框是检测来的**（批量跑时）。8 张单跑时用的是查表固定的框，好让 inpainting 的结论
   不被检测误差污染；批量脚本接了检测器，于是**检测的错**（找不到框、找到多个框）会
   进入统计 —— 这既是真实使用时的情形，也意味着批量里的失败要按「检测 / 定位 / 擦除 / 排版」
   分开数，才知道该改哪个文件。
   ⚠️ **最阴的一类检测错是「框跨两行评论」**：框高 96 里装的是**两行**文字（段高 51~103，
   而单行字高只有 27~32）。它**四道判据全绿** —— 擦得干净、间距对、尾块对、不越框，
   因为四道判的都是**几何自不自洽**，没有一道问「框里该有几行」。实测 **10 张**
   （`一麻袋开心(沧海一舟)-6/1.jpg`、`宝宝不乖-3/2.jpg`、`惊雷-4/2.jpg`、`星空-7/6.jpg`、
   `爱尖叫的麦子-3/1.jpg`、`稻香-3/3.jpg`、`肘死你-110/34.jpg` 与 `96.jpg`、
   `风过无恨-10/3.jpg`、`魂殿抖音分殿殿主-5/2.jpg`）。
   **定位侧自 2026-09-30 起会把它按行带切开**（只动名字那一行，见 §3.1.1），
   但**检测端（框为什么会圈大）没修** —— 出来的片仍然是「只改了半条评论」。
   ⇒ **统计上的「零违规」不等于「出的片对」。**
5. **「放不下就截断」是规格，不是缺陷。** 名字写长 + 版面不变，本身无解：三档取舍
   （`clip` 砍字 / `width` 缩字号 / `height` 什么都不做）里必须选一个代价，
   默认选的是「保字号、砍字」。

## 6. 批量验证：650 张真实语料

**为什么必须做**：§5 第 3 条 —— 最初那 8 张全出自**同一个用户目录**，是同一版式的 8 次重复。
批量不是为了「跑得更多」，是为了让结论能承受「你的样本其实是同一张图」这句话。

```bash
python3 core/batch_run.py /home/puyu/work/data/抖音奇瑞汽车/all_users_正面_3张以上
```

650 张 / 112 个用户目录 / 8 进程 / **约 3.3 分钟（0.31s/图）/ 0 元**。
报告落 `outputs/batch_20260930_100956/`（`rows.csv` + `summary.json` + `skipped.txt`），
**外加 551 张 `dump/<用户>/<序号>_probes.png`**（`--dump all`）。
551 = 650 − 88 跳过 − 11 `NO_BOX` —— 没有框就没有裁剪区，跳过的图按规格也**一张都不落**。

### 跳过：88 张，**不是失败，也不计入任何数量**

按 2026-09-30 的规格「**含有表情也跳过，跳过的不记入数量，跳过的要记绝对路径**」，
650 张里有 **88 张**被摘出去：

| 跳过理由 | 判据 | 判在哪一步 | 张数 |
|---|---|---|---|
| `SKIP_PURE_EN` | 昵称串**只有 ASCII** | **读图之前**（目录名/`交付清单.txt`） | **60** |
| `SKIP_EMOJI` | **原图**用户名段里有 emoji | **定位之后**（图上像素） | **28** |

跳过 = 不擦不画、**不落任何图**，而且**不计入任何数量**：不进 `failures`、
不进 `failure_counts`、不进 `by_probe` 的分母，**也不进 `run.images`**。
`rows.csv` 各记一行（`probe="-"` + `skip` / `skip_note` 两列），`summary.json` 单出
`skipped` 块 —— 那里 `run.images` / `images_processed` 是**处理数**，`images_scanned`
才是扫到的总数。

**跳过的图要留绝对路径**：`rows.csv` 的 `path` 列（每一行都有，`Path.resolve()`）＋
一份 `skipped.txt`（本批 **88 行**，一行一个「绝对路径 TAB 理由 TAB 证据」）。

⇒ **真正进统计的是 562 张**，其中 11 张检测不到框，**可定位的分母是 551 张**。

**这 88 张不是「损失」**：昵称整段是 ASCII 时「保持总长不变」没有意义；含 emoji 的原图
名字上，那枚 emoji 的位置要么空着、要么被随机补的字盖住。跳过规则把它们从「成功」移到了
「不该出片」（88 张里 **78 张**原本定位是成功的）。

⚠️ **这 88 张一张都没进过管线** ⇒ 三个失败家族、`NO_BOX`、定位成功率都**与跳过规则无关**：
它们只是不出片，不改任何一张**未跳过**图的结论。（两件事要分开记：本轮定位数从上一版的
**464 变成 496**，那是**定位改进**——字带/行带 + 徽章判据 + 徽章兜底——带来的，不是跳过规则动的。）

### 结果

| | 找到多个框 `MULTI_BOX` | 50 / 551（9.1%）—— 其中 **34 张定位仍成功**（按面积取最大那个是对的） |

⚠️ **「不越框 ✓ 1488/1488」要按它的口径读**：`box_ok` 量的是**框右界之外**零改动，
**上下方向不在内建判据里** —— 那是由**定位的行带**按构造守的（改动夹在名字那一行的
上下界内），判据 ⑦ 是它在 8 张上的复核。这条口径**真的漏过一次**：`A携酒话清风D疗-5/1.jpg`
的 `short` 档在绿框上沿外 2px 改了 54 个像素而批量照报绿（字高被描边抗锯齿残渣撑到 84px、
字号算成 88px），见 §3.1.1 与 §4 的 ⚠️，**bug-166 已修**。

**多行框 10 张**（检测器圈大了）自本轮起按行带切开：只动名字那一行，第二行原样留着
（独立脚本复量：距行带 >3px 的改动 0 像素）。报告末尾单列一行，`rows.csv` 有 `multi_line` 列。

**这是本轮最重要的一个数**：`DIRTY`（擦不干净）与 `LEAK`（蒙版外被改动）在 1488 次里
**一次都没出现**。这两类在本地路线上是「**不该**出现」的 —— 插值物理上不会造字，
「只贴蒙版内」让蒙版外零改动成为构造保证，出现即代码 bug（对照：API 路线 14 张里
4 张造字、擦干净 3 张）。**失败全部发生在「定位」这一步之前**；一旦定位成功，
后面两步 1488 次零违规。

截断按长度分层，符合规格预期：

| 探针 | 名字 | 新名字宽 / 槽位宽 | 截断张数 |
|---|---|---|---|
| `short` | `A` | 1.01 | **0** |
| `equal` | 目录名里的昵称 | 1.02 | 15 |
| `long` | `SuperUser` | 1.38 | 217 |

⚠️ `short` / `equal` 的宽度比都是 **1.01 而不是「明显小于 1」**，是**补满槽位**
（`FILL_SLOT_ENABLED`，2026-09-29 规格）**按构造**决定的：名字比槽位窄时随机补字补到
≈ 槽位宽，好让尾巴不动、总长不变。关掉它（`--no-fill`）才回落到旧口径的 0.26 / 0.96。
`long`（1.39）补不进去，只能截断。

### 定位失败的 71 张，三个家族

| 家族 | 张数 | 什么情况 | 例 |
|---|---|---|---|
| ① 有 ≥60 的饱和段，但凑不成「名字 + 冒号」 | **39（54.9%）** | 昵称里带 **emoji** —— emoji 是**实心团块**，被「填充率 ≥0.60 判徽章」的规则剔掉了，剩下的文字段不够拼出结构 | `A淘气⇒-3/1.jpg`（昵称真身是 `🦄淘气💨`，见下） |
| ② 框内**没有**任何 ≥60 的饱和段 | **27（38.0%）** | 昵称本身不饱和（淡灰蓝的 `czy`），或者**框根本不是评论行** | `A携酒话清风D疗-5/4.jpg`（整框最大彩度只有 51）；`肘死你-110` 的 4 张 |
| ③ 有用户名段，但其后没有冒号段 | 5（7.0%） | 结构判据的边界 | `八方来财-3/1.jpg`、`肘死你-110/57.jpg` |

⚠️ **家族 ① 是「定位」的问题，跳过规则接不住**：emoji 在**名字聚类之前**就被当徽章剔了，
名字压根没定位到。而两条跳过判据一条看**昵称串是不是纯 ASCII**（读图之前就判，不读图）、
一条看**已经定位到的**名字段里有没有 emoji —— 两条都够不着它。
所以「emoji 把定位搞挂」只能以**定位失败**的形态出现，永远轮不到跳过规则去接。

**这三个家族在原来那 8 张上一张都不存在** —— 那 8 张的昵称一律是纯青色汉字、无 emoji、框都对。
所以批量的价值不是「再确认一遍」，而是**把结论从「这个版式」收窄到它真正的适用面**。

⚠️ 家族 ① 属于**多色 emoji / 团块抢色**这一类 —— `core/inkmask.py` 是按**最简情形**写的，
本来就没处理这一层，所以它只能以**定位失败**的形态出现，而不是被当成 emoji 判出来。

### emoji 判据的标定（2026-09-29 起**只作诊断**）

`SKIP_PURE_EN` 是字符串判断（`str.isascii()`），没有标定可言 —— 它是现在**唯一**的跳过判据。
下面这一节是上一版 `SKIP_EMOJI` 用过的 emoji 判据：规格改成「**含表情不跳过**」之后，
它**不再用于跳过**，但仍在跑、仍会进日志（`EraseRegion.name_emoji` / `Outcome.has_emoji`），
所以标定照旧有效、照旧值得记 —— 排查「名字段里哪几段不是名字文字」时要靠它。

判据**只能从图里判**，不能看目录名：目录名会把 emoji 转写或直接丢掉
（`A淘气⇒` 的真身是 `🦄淘气💨`；`A携酒话清风D疗` 的 emoji 一个字都没进目录名）。
判据也只判**用户名段**（徽章、冒号、正文里的彩色像素不算）。

**判据**：名字段里，凡**核心色彩度**落在名字文字的色带**之外**的段，就是 emoji。
`inkmask._emoji_in_name` 只看**已经定位到的**那几段（`name_idx`），先过三道噪声闸：

| 闸 | 值 | 挡的是什么 |
|---|---|---|
| 墨迹像素 ≥ | 120 | 汉字的一小截笔画（实测 36 px）—— 它是背景与笔画的混色，彩度天然偏低 |
| 段宽 ≥ | 10 | 同上，笔画碎片（最小的一枚真 emoji 宽 17） |
| 段高 ≤ | 45 | **跨行的段**：框里含两行评论时会出现高 51~103 的段，彩度也不对，会被误当 emoji |

彩度的上下闸是**量出来的**。650 张语料里，过完三道闸的 **1060 个名字段**：

| 彩度 | 段数 | 是什么 |
|---|---|---|
| 30 ~ 59 | 6 | 低臂：`🍼` 这类**浅色** emoji（32~36），另有两处碎片误报 |
| **60 ~ 82** | **1018** | **名字文字本身**（70~80 是主峰，最大 82） |
| 90 ~ 100 | 3 | 跨行的段（高 51~103）—— 不是 emoji，是多行框（被上面那道高闸挡掉） |
| 101 ~ 199 | **21** | emoji：😊👍💙🈚✨🌈🖐（**最小 101**） |

⇒ 取 `NAME_EMOJI_SAT_MIN = 60`（= `USERNAME_SAT_MIN`，与桥接判据**同源**：
被桥接进来的段就是「靠宽度像 emoji」的段）与 `NAME_EMOJI_SAT_MAX = 92`。
空档是 **83~100**，92 到两侧各留 10 / 9 的余量。

⚠️ **尺子不能混用**：`inkmask` 的「彩度」是 `max(core) - min(core)`（色度），
不是 OpenCV `COLOR_RGB2HSV` 的 `S`。同一枚 🌈，色度 190、HSV 的 S 是 204；
名字文字色度 ≤82、HSV 的 S ≤88。在 HSV 那杆尺子上，文字与 emoji 只差 6，**分不开**。

**实测报出 emoji 的 9 个用户**（28 张，占语料 4.3%）：
`A携酒话清风D疗-5`、`✨神秘人-3`、`佳-4`、`八方来财-3`、`小熊饼干-4`、`心想事成-3`、
`無10-5`、`绿愿-4`、`预见-3`。
规格改成「含表情不跳过」之后，这 28 张**照常出片**（实测全部定位成功）。

**两条实测否决的替代判据**（记下来免得重走）：

- **σ（核心像素 RGB 标准差）** 不是 emoji 信号：它把纯汉字用户（`幽幽` 50.4、
  `魔熙魔熙` 47.8）判得比真 emoji 用户（`A携酒话清风D疗` 41.4）还高 ⇒ 弃用。
- **按图量行高**（槽位内墨迹的最长连续行段）当「跨行闸」：在 `幽幽-18/11.jpg`、
  `军陌-4/3.jpg` 上两行文字的行投影根本不缝开，量出 60 / 77，闸门形同虚设
  ⇒ 改成绝对像素值 45（本语料单行字高 27~32）。

**已知误报**（650 张里只有这 2 处）：`qzuser-13/9.jpg`（彩 56）、`yyyuuu-3/1.jpg`（彩 59），
都是纯 ASCII 昵称里被桥接进来的**笔画碎片**（宽 14、高 16）。两者都属于纯英文昵称，
**在读图之前**就已经被 `SKIP_PURE_EN` 摘掉了，走不到这条判据。

⚠️ **换语料先复核**：昵称本身就是红/橙等高彩度色时，彩度也能到 200+，这条判据会误判。
本语料 112 个昵称全是青/白/灰蓝，实测最大 82。

### 语料账目：652 vs 650，差额已定位到 2 个文件

`交付清单.txt` 写 **652 张**，磁盘上是 **650 张**。差额不是「大约 0.3%」，
而是**精确的 2 张**，且**出处确定** —— 目录名 `昵称-张数` 自带张数，逐目录核一遍：

| 目录 | 名字声称 | 磁盘实际 | 缺的是 |
|---|---|---|---|
| `爱国者-9/` | 9 | **8** | `1.jpg`（现存 `2.jpg`…`9.jpg`） |
| `qzuser-13/` | 13 | **12** | `1.jpg` |
| 其余 110 个 | — | — | 全对 |
| **合计** | **652** | **650** | **2** |

⇒ **两张 `1.jpg` 在归档/解压环节丢了**，不是统计口径问题。这也解释了 §5 第 3 条那句
「原 8 张不在任何归档里」：`mock_scale/data/` 的那 8 张经 md5 比对**就是 `爱国者-9/` 的全部 8 张**
（8/8 命中）—— 它们不是「不在归档里」，而是**归档里那个目录少了 `1.jpg`，
仓库里这 8 张是从它拷出来的**。

⚠️ **由此得两条**：① 报数时写「650 张（清单称 652，缺 2 张 `1.jpg`）」，
不要含糊成「约 650」；② `equal` 探针用目录名当新名字，而**目录名的张数不可信**
（112 个里 2 个是错的）—— 名字部分（`昵称-张数` 的 `昵称`）不受影响，但**别拿目录名的
张数当任何统计的真值**。

**样本量分布也是偏的**：112 个用户里 50 个只有 3 张，而 `肘死你-110/` 一个目录就有
**110 张（占全语料 17%）**。⇒ 按图统计的数会被这一个用户主导；要报「按用户」的成功率，
得先按用户聚合再平均，不能拿 650 张直接除。

### 锚点自检

批量脚本内置一条自检：`爱国者-9`（原 8 张出自这里）在 `equal` 探针上必须**全绿**。
跑完结果 **8/8 全绿 ✓** —— 说明批量外壳与单张跑是一致的，上面这些数不是外壳错出来的。

> 这条自检是这个脚本**唯一**的自我验证手段。没有它，「批量跑出来的数」和「管线真的
> 是这个数」之间就只隔着一层信任。


| 文件 | 职责 |
|---|---|
| `core/config.py` | 全部常量（框表、阈值、字体、取舍策略、检测器参数） |
| `core/inkmask.py` | 定位：框内找「用户名 + 冒号 + 尾巴」→ 擦除蒙版 + 几何 |
| `core/inpaint_local.py` | 擦除：telea / ns / flat 三策略 + 洗源 + 度量 |
| `core/draw_text.py` | 排版：`plan_name` / `shift_tail` / `render_name` |
| `core/replace_username.py` | 单张主流程 + CLI（含两条硬校验的实测值） |
| `core/box_detect.py` | 标注框检测（**移植件**，批量跑才用） |
| `core/batch_run.py` | 批量：检测 → 定位 → 擦除 → 排版，逐段判对错 + 报告 |

批量跑完在 `outputs/batch_<时间戳>/` 落 `rows.csv`（每图 × 每探针一行，含 `path` 绝对路径列
与 `multi_line` 列）、`summary.json`（分组汇总 + 失败分类 + 锚点自检 + `skipped` 块）与
`skipped.txt`（跳过的图一行一个绝对路径 + 理由；**没有跳过就是空文件/不落**）。
**默认不存结果图** ——
650 张 × 3 个探针 ≈ 1950 张 PNG，是几个 GB 的纯浪费。要看效果用 `--dump`：

| `--dump` | 落什么 |
|---|---|
| `none`（默认） | 只落 `rows.csv` + `summary.json` |
| `failures` | 再加有失败判据那几张的 `<序号>_<探针>_{replaced,compare}.png` |
| `all` | 每张图都落 `dump/<用户>/<序号>_probes.png`（**裁剪**摞图） |
| `full` | 每档两张：`<序号>_full_<档>.png`（整张尺寸）+ `<序号>_<档>.png`（裁剪条），另加 `<序号>_orig.png`（原图基准条） |

⚠️ **`all` 看探针效果必须用摞图**（原图 + 短 + 等长 + 超长，共 4 行）。三档各存一个
**裁剪**文件是**看不了**的：得来回切三张图比对，而且三张图的**内容对不齐**（名字越短、
尾巴平移越多）—— 等于存了但没看。摞图把 4 行按同一个裁剪区对齐、左侧标出探针名与实际
写进去的名字（`✂N` 表示截掉 N 个字），长度的影响才是一眼可见的。

`full` 是另一回事，看的是**整屏观感**：换完名字跟右边的按钮/头像挤不挤、整条评论有
没有失衡 —— 那些恰恰在框外。形态在 **2026-09-29 按用户反馈重做过**，推翻的是上一版的
「把四行摞图贴回原评论位置」：那块面板带着留白，会把上下的邻居评论和左侧等级徽章一起
盖住，而看图上分不出那是贴图盖的还是管线改的。

两条规矩：

* **替换只发生在绿框内**。`_full_<档>.png` 就是管线自己的结果图，不做任何裁剪拼贴 ——
  框外逐像素等于原图（本地路线的构造保证，`rows.csv` 的 `outside_changed` 逐行量出来
  是 0，独立脚本按框复量 69 张里 68 张为 0）。
* **一档一张**。探针没出图（定位失败）时**不落整图，但落裁剪条**：原图那一条加红框写上
  失败标记，否则「这一档没跑」和「跑了但失败」在目录里长得一模一样。

检测不到框的图没有裁剪窗，`full` 下不落图（看 `rows.csv` 的 `NO_BOX`）。

```bash
# 650 张全存裁剪摞图（~120MB，跑一次 ~5 分钟）
python3 core/batch_run.py <语料根> --dump all

# 650 张全存「每档一整图 + 裁剪条」（~5.7GB，约 8.7MB/张原图）—— 配 --limit 跑
python3 core/batch_run.py <语料根> --dump full
```

## 8. 三条别忘的约束

改这套代码、或把它挪去别处之前，记住这三条（都是踩出来的）：

* `shave_frame` 与 `tail_margin_right` 的常量都是**为这个语料量出来的**（绿描边、2px 边距），
  换语料要先复核，不是普适规则；
* **平移 ≠ 重画**：要保住「冒号 + 正文」的像素就必须贴原图块，重画必然差 1~2px；
* **顺序**：任何「腾空 + 贴片」都必须在该区域最终绘制**之前**做
  （先搬尾巴、后写名字，反了就啃掉名字 —— §3.4）。
