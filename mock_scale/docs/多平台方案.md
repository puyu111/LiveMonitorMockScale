# 多平台方案：一套管线怎么同时跑抖音 / 视频号 / 微博（+ 快手 App）

**结论先行：不要做「一个阈值适配所有平台」—— 已经被实测否决。真正的做法是
「把平台差异收进一个 profile + 把定位的锚点从『颜色』换成『冒号』」。**

依据：三份语料的逐段量色（2026-09-30 实测，见 [`全流程说明.md`](全流程说明.md) §12 边界）：

| | 抖音（主语料） | 视频号 | 微博 |
|---|---|---|---|
| 名字段彩度 | **74**（青蓝 `RGB(165,218,239)`） | 2（白 `142,143,144`） | **0**（灰 `188,188,188`） |
| 正文 | 白（彩度 4~6） | 白 251（+ **❤️ 贴纸 142~145**） | 纯白 254 |
| 框内 ≥60 的段 | 名字 + 徽章(55~60) | 只有正文里的贴纸（在名字**右边**） | **一个都没有** |
| 框内众数色占比 | 中位 51%（43~60%） | **9~10%**（2 张） | 中位 58% |
| 纯英文昵称跳过率 | 9.2%（60/650） | 18.1%（76/420） | **3.7%（15/406）** |
| 定位结果 | 464/551 = 84.2% | **0/17** | **0/8** |

**一句话：`USERNAME_SAT_MIN=60` 这条判据是抖音专有的，它在另外两个平台上不是「偏一点」，
而是 0 命中。** 而**排除定位之后的所有环节**（擦除 464/464 干净、排版 1392/1392 合规、
失败在定位之后一次都没出现）已经证明是**平台无关**的。

## 1. 平台差异到底落在哪几处（先划清边界）

把整个管线按「平台相关性」分三层，改造只动第一层：

```
① 平台相关（要参数化 / 换算法）
   ├─ box_detect：描边颜色 profile（绿/紫 → ？）+ 「框里几行」判据
   ├─ inkmask.find_erase_region：规则 3 徽章 / 规则 4 名字 / 规则 5 冒号   ← 病灶
   └─ config：USERNAME_SAT_MIN、BG_DIST_THRESH、shave_frame 绿色判据、FILL_SLOT…
② 规格相关（要和用户确认，不是技术问题）
   └─ SKIP_PURE_EN 是否适用、FILL_SLOT「总长不变」是否适用、equal 探针取目录名
③ 平台无关（已实测，一行都别动）
   └─ inpaint_local.erase（洗源 + 只贴蒙版内）· draw_text（plan/shift/render）· 判据体系 · 报告
```

**验收线**：改造之后，抖音 650 张的结果必须**逐图不变**（同 slot / colon / join_gap / 合规数）。
本项目已有先例 —— bug-164 就是「自己引入的回归」，靠 40 张逐行 diff + 全量命中数对账抓出来的。

## 2. 核心改动：定位的锚点从「颜色」换成「冒号」

### 2.1 为什么必须是冒号

冒号是**三份语料里唯一都稳定的特征**（实测）：

| | 段宽 | 填充率 | 位置特征 |
|---|---|---|---|
| 抖音（数据/ 那 8 张） | 4~5px | ~20% | 墨迹偏**下半**（`colon_rows`）⚠️ 见下 |
| 视频号 | 5~6px | 15~25% | 同上 |
| 微博 | 5~6px | 26~32% | 同上 |

而「名字的颜色」三份里两份完全不成立。所以：

```
名字 := 冒号左边、与之相邻的那一串「文字段」
徽章 := 名字左边那个「实心宽块」（width ≥ 40 且 fill ≥ 0.60 —— 这条判据本身跨平台成立）
```

**判据从「颜色」换成「结构 + 几何」**，颜色降级为**可选的辅助信号**（见 §2.3）。

### 2.2 冒号候选的判据（四道闸，全部平台无关）

1. **窄**：段宽 ∈ `[4, 8]`（`COLON_MAX_WIDTH=8` 已经是现成常量）；
2. **低填充**：`fill ≤ 0.35`（冒号是两点，汉字 0.37~0.49、徽章 0.74）；
3. **不高不矮**：段高 / 字带高 ∈ **0.4~0.8** —— 这一条最狠：字母 `l`/`1` 和汉字占满整行
   （>0.8）、句点逗号只有 ~0.2（<0.4），只有「：」是两点、约占 0.65 行高。
   ⚠️ **别用「只看下半行有没有墨」当判据** —— 那是**错的**：`数据/` 那 8 张的冒号恰好在下方，
   于是当年记成「冒号只有下半截」；而 `军陌-4/3` 的冒号**上点在行中线之上**
   （行 897-900 与 909-913，字带 891-916 ⇒ 上点顶在 0.23 处）。窄+高度区间才是跨语料的判据；
4. **右边是长正文**：冒号右侧隔一个空隙有宽度 ≥ 60px 的文字段。

四道全过才认。多个候选时取**右边正文最长**的那个（正文越长越像真的分界）。

### 2.3 颜色退到哪里去（不删，降级）

`USERNAME_SAT_MIN` 保留，但只在**两种情况下**用：

- **tie-break**：多个冒号候选、正文长度接近时，优先选「左边段与抖音彩度主峰接近」的；
- **平台自检**：给报告打一个平台标签（见 §3），并在**抖音 profile** 里保持现在的行为
  （`name_strategy="saturation_run"`），保证零回归。

## 3. 平台 profile：`config.PLATFORMS`

```python
@dataclass(frozen=True)
class PlatformProfile:
    name: str                       # "douyin" | "wechat_channels" | "weibo" | "generic"
    name_strategy: str              # "saturation_run"（抖音，现状）| "colon_anchor"（其余）
    username_sat_min: int           # 仅 saturation_run 用
    colon_w_range: tuple[int, int]  # (4, 8)
    colon_fill_max: float           # 0.35
    colon_lower_half_only: bool     # True —— 三平台通用
    badge_min_width: int            # 40
    badge_fill_ratio: float         # 0.60
    frame_colors: tuple[str, ...]   # 框描边颜色档（"green" / "purple" / "auto"）
    bg_mode_share_min: float        # 背景众数色占比下限（低于它 ⇒ 拒跑，见 §4）
    skip_pure_en: bool              # 这条**规格**是否启用（见 §5）
```

**平台从哪来 —— 不要猜，从路径里取。** 实测三批语料的路径形状是一样的：

```
/home/puyu/work/data/<活动名>/<平台名>/all_users_正面_3张以上/<昵称-张数>/<n>.jpg
                                  ^^^^^^ 抖音奇瑞汽车 / 视频号 / 微博
```

```bash
core/batch_run.py <根> --platform auto     # 默认：从路径里的平台段取，取不到再探测
core/batch_run.py <根> --platform weibo    # 显式指定
```

`auto` 的探测判据（用 §6 的探针量出来，不靠猜）：
**名字段彩度主峰 ≥60 ⇒ 抖音型；≤5 且「名字亮度 < 正文亮度 − 40」⇒ 灰/白名字型。**

## 4. 背景前提要变成「前置检查」，而不是隐含假设

视频号那 2 张「整框只切出 1 段」的失败，本质是**背景不是近纯色**（框内众数色只占 0.8~1.6%，
有一张框整个跨在亮/暗交界上）。现在的表现是**伪装成「找不到名字段」**，排查时得手工算才发现。

方案：定位之前加一道体检，不通过就**明确拒跑**：

| 检查 | 判据 | 不通过时 |
|---|---|---|
| 背景是否近纯色 | 框内众数色占比 ≥ `bg_mode_share_min` | `NO_LOC:BG_NOT_FLAT` |
| 框是否跨行 | 框内行带数 ≥ 2 且带间有背景间隙 | `NO_LOC:BOX_SPANS_LINES`（已有行带机制，改成在**检测**层就报） |

**新失败码的意义**：把「这份语料不适合这条路线」和「我们的代码有 bug」分开。
现在两者都落成 `LOC_NONE`，看不出区别 —— 这正是这两轮排查每次都要人工量色半小时的原因。

## 5. 规格层：这两条必须回去问用户，不能默认照搬

1. **`SKIP_PURE_EN`（纯英文昵称跳过）** —— 三份语料全量实测：抖音 9.2%（60/650）、
   视频号 18.1%（76/420）、微博 **3.7%**（15/406）。
   ⚠️ **我先在这里写错过一次**：当时拿 `--limit 20` 的样本报「微博 60%」，全量一跑只有 3.7% ——
   因为 `--limit` 取的是任务表**前 N 条**（按目录名排序），那 20 张里正好有 `coco12246364429281-4`
   和 `yoyo_light-11` 两个纯英文目录。**这正是 README 里早就写过的抽样陷阱，我又踩了一次。**
   ⇒ 开关已实现：profile 的 `skip_pure_en`（微博默认 **false**，即不跳过），
   `--no-skip-pure-en` 语义并入 profile。跳过数仍按理由打印在报告里。
2. **`FILL_SLOT`（名字不够长就随机补字补满槽位）** —— 这条是抖音的「总长不变」规格。
   视频号/微博是否同样要求？**这是产品问题**，`--no-fill` 已经能复现旧行为，缺的只是确认。

> ⚠️ 这一节的结论是：**阈值要按平台复核，规格同样要按平台复核。**

## 6. 先做这个：`platform_probe.py`（最高性价比）

连续两批语料「整批 0 定位」，而每次定位原因都要人工裁图 + 逐段量色。**把这几轮的手工活固化成一个命令**：

```bash
python3 platform_probe.py <语料根> --limit 5
```

输出（每张一行 + 一段汇总）：

```
平台判定：weibo（依据：名字段彩度主峰 1，名字亮度 188 < 正文 254）
框检出  5/5 · 多框 1 · 疑似跨行 0
名字段彩度：  0~5: 5 张   60~80: 0 张   （⇒ 彩度判据不可用）
冒号候选命中：4/5 张（宽 5~6px · 填充 26~32% · 高 0.6~0.7×行带 ✓）
背景众数色占比：中位 22%（≥15% ⇒ 背景可用）
纯英文昵称跳过率：12/20 = 60%   ⚠️ 这条规格在本平台会吃掉六成
建议 profile：weibo（name_strategy=colon_anchor, skip_pure_en=false）
```

**它几乎就是把这几轮诊断固化成代码**：框检出率、名字段彩度直方图、冒号候选命中率、
背景众数色占比、纯英文跳过率。跑一次 10 秒，就能回答「这份语料能不能跑、该用哪套 profile」，
而不是跑 650 张然后看一片 `LOC_NONE`。

## 7. 落地顺序（每步都可独立验收）

| # | 做什么 | 验收线 | 风险 |
|---|---|---|---|
| 1 | **`platform_probe.py`**（新增，不动管线） | 在三份语料上给出与本次人工诊断一致的判定 | 无 —— 纯读 |
| 2 | **`config.PLATFORMS` + `--platform auto`**（常量搬家） | 抖音行为逐图不变（跑 `data/` 8 张 + 650 张抽样） | 低 |
| 3 | **`colon_anchor` 定位策略**（新分支，抖音仍走 `saturation_run`） | 视频号/微博不再 `LOC_NONE`；**抖音 650 张逐图零回归** | 中 —— 这是主改动，必须对账 |
| 4 | **背景前置检查 + 新失败码** | 视频号那 2 张从 `LOC_NONE` 变成 `BG_NOT_FLAT` | 低 |
| 5 | **规格开关 + 报告加 `by_platform`** | 微博那批抬头显示「跳过 60%」 | 低 |
| 6 | 框检测按平台补标定 `frame_colors` | 三平台 `NO_BOX` 率 | 低 |

**顺序不能反**：第 3 步是唯一会动到定位结果的改动，必须在第 1、2 步（有了探针和对账手段）
之后做，否则回归看不出来。

---

## 8. 明确不做的事

- ❌ **不做「一个阈值通吃」** —— 已被实测否决（灰名字彩度 0、纯白正文彩度 0，两者不可分）。
- ❌ **不给 `core/inkmask.py` 再叠一层更重的「文本几何」** —— 那是另一套依赖 + 另一份语料硬化。
  但那个思路**要借鉴**：「本色墨迹投影（背景色→文字色轴）」正是「灰名字 vs 白正文」的正解 ——
  **按亮度分层，而不是按色相**。第 3 步的 `colon_anchor` 只解决「找到哪里是名字」，
  若之后还要判「名字里哪几段是文字」（emoji 桥接那一类），该沿用这个思路。

## 实测结果

| 语料 | 张数 | 平台判定 | 改动前 | 改动后定位 | 定位成功后的合规 |
|---|---|---|---|---|---|
| 抖音（主语料） | 650 | douyin / saturation_run | 464/551 = 84.2% | **496/551 = 90.0%** | 496/496，三档合计 **1488/1488** |

**「定位成功即合规」在三份语料上都是 100%** —— 这是本文开头的判断（平台差异只在定位一层）拿到的实证。

### 抖音那 +16 张的归因（重要）

抖音定位从 464 涨到 480。**这 16 张不是本次多平台改动的功劳**，逐张对照实验证明是
**另一轮改动加的「笔画粗细」徽章判据**（`stroke_peak` / `BADGE_STROKE_MAX`）修好的：
把那条闸关掉（`BADGE_STROKE_MAX=999`）这 16 张**全部退回失败**，开着全部成功。

本次改动对抖音的零回归证据：① 0 张退步；② 锚点自检 `爱国者-9` 8/8 全绿；
③ `group_cols`（尾巴组）在抖音路径上是**严格恒等**的 —— 该路径下名字与冒号之间必然没有别的段，
`range(name_idx[-1]+1, colon_idx)` 恒为空。

## 门槛是量出来的，不是拍的（五道闸的实测值）

| 闸 | 取值 | 实测依据 |
|---|---|---|
| 宽 | 4~8px | 三份语料真冒号 4~6px；汉字 26~32px |
| 填充率 | ≤0.45 | 真冒号 0.15~**0.37**（微博最高那张撞到原定的 0.35 ⇒ 漏掉）；汉字 0.37~0.49（被宽度闸挡） |
| 段高 / 行带 | 0.40~0.80 | 真冒号 **0.59~0.63**；正文里的逗号只有 **0.26**（4.jpg 曾被它抢走）；汉字 0.93~1.00 |
| 上缘位置 | ≥0.20 | 真冒号 **0.28~0.30**；汉字 0.00~0.11。⚠️ 原来拍的 0.35 会把**真冒号**挡掉，而且报的是「没有候选」，看不出被门槛挡的 |
| 右侧正文 | ≥60px | 冒号必须是个分界，右边得有东西 |

## 实施中踩到的三个坑（都已修）

1. **白/灰名字被整片报成 emoji ⇒ 批量会跳过每一张图。** `NAME_EMOJI_SAT_MIN/MAX=60/92` 是在抖音
   标定的（名字彩度 70~82），视频号/微博的名字彩度 0~5 **落在带外** ⇒ 名字本身被报成 emoji，
   而 `SKIP_EMOJI` 据此跳过整张图。修法：非抖音平台按**名字段自己的彩度中位数 ±15** 现算色带 ——
   抖音名字中位 76 ⇒ 算出 61~91，**正好复现**标定的 60~92（这也是 15 这个数的依据）。
2. **徽章可能夹在名字与冒号之间。** 微博是 `[名字][铁粉牌][：][正文]`，抖音/视频号是
   `[牌][名字][：]`。原来「向左走撞到徽章就停」取不到微博的名字；改成**跨过徽章继续往左**
   （牌子一律不进名字）。随后又发现：**牌子还得跟着尾巴一起走** —— 否则「名字右缘之后的第一条
   墨迹列」会把它当成冒号，间距判据当场报 `GAP_BAD`（微博 12 张里 4 张中招）。
   尾巴组的左界因此改成「名字与冒号之间的一切」。
3. **`--limit 20` 的抽样假象**（见 §5 的更新）：害我把微博跳过率写成 60%，全量只有 3.7%。
4. **微博的药丸夹在名字与冒号之间 ⇒ 名字取色被药丸染黄**（bug-180，用户报「颜色问题」）：
   `span`（名字首段→冒号末段）把药丸圈进去，而取色取「最亮 25% 均值」，药丸是亮实心牌
   ⇒ 灰名字 `RGB(188,188,188)` 被拽成 `RGB(211,189,153)`（R+23/B−35，肉眼就是发黄）；
   字带也被药丸的行范围撑大。**修法就是「不同平台走不同逻辑」**：新增 `_core_color_of`
   （按列掩码取色），`colon_anchor` 平台改用**名字自己的列**取色与量字带，抖音一字不改。
   ⇒ 抖音 650 / 视频号 420 全量逐项不变，微博只有截断 2/54→0/52（字带量准的连带修正）。

## 追加：两行框的三个病灶（2026-09-30 第 2 轮，用户报 `军陌-4/3` / `一麻袋开心(沧海一舟)-6/1`）

「框跨两行」不是**一个** bug，是**三个**，修完才看清：

| # | 病灶 | 症状 | 修法 |
|---|---|---|---|

## 追加：取色窗口被污染过三次（2026-09-30 第 3 轮，用户再报「颜色有问题」）

**「取一段文字的颜色」这个动作，窗口必须同时夹列和行** —— 两行框里两边都会漏，而且漏进来的
脏东西每次都不一样，三次实测：

| 混进来的是谁 | 名字本色 → 画成 | 图 |
|---|---|---|
| 夹在名字与冒号之间的**药丸**（微博 `[名字][铁粉牌][：][正文]`） | `(188,188,188)` → `(211,189,153)` 淡金 | `yoyo_light-11/5` |

| 同上 | `(166,218,238)` → `(220,210,133)` **发黄** | `一麻袋开心(沧海一舟)-6/5` |
| 紧跟名字的**「冒号」段其实是与正文连成一段**的（112px 宽、含正文白字） | `(164,220,236)` → `(247,248,253)` **近白** | `军陌-4/3` |

⇒ 取色窗口**两条策略统一**成「**名字自己的列**（`name_idx` 的并集）∩ **名字所在的行**（`row_keep`）」。

⚠️ **两个教训**：
1. **bug-180 我按「平台分叉」只修了 `colon_anchor`，抖音那条路径的同类污染就漏掉了** ——
   修「窗口/口径」类 bug 时，要先问「**另一条路径上对应的脏东西是什么**」，别因为「它没报错」就以为它干净。
2. **等价性论证是敢改共享代码的底气**：新窗口与旧口径在**单行框**下等价（名字的墨迹本来就在字带内），
   所以这个改动只影响两行框/有夹层的图 —— 这就解释了它为什么没带动 650 张。

# 追加：快手 App 端（2026-11-02，CTCC 8.8 交付树）

快手是**第 5 个平台档**（`platforms.PROFILES["kuaishou_app"]`），也是第一个
**不能只靠「框 + 冒号锚点」直接跑**的平台。它带来两个新的**平台级选项**，都已实现为
profile 字段（默认关 ⇒ 其它平台逐字节不变）：

| 字段 | 快手取值 | 为什么 |
|---|---|---|
| `needs_geom` | `True` | 交付树的彩色框是**多行融合框**（ROI 来自 comments 的组块，常装 2~6 行）；目标行**不一定是第一行**（750 张里 91 张不是）⇒ 必须用 `comments.jsonl` 的 `colon_box` 定行 |
| `geom_row_from_colon` | `True` | 有 geom 时把取样窗口的**纵向**收到 `colon_box` 那一行（±min(12, 0.8×冒号高)），并丢弃带外的 `badge_box`/表情 |
| `bg_quantize` | `32` | 卷轴底是叠在视频上的深色半透明层；精确众数会被**白字**抢走（实测白字 100 个同色 vs 暗底每种 ~90 个 ⇒ 背景估成白色、墨迹占比 0.90）。按 32 分桶取众数桶均值后，背景占比最低 24% |

## 量出来的参数（750 张，只统计「目标行」的选中候选）

| 闸 | 快手实测 | 取值 |
|---|---|---|
| 冒号列段宽 | p5~p75 = **3px**，p95~max = 10 | `(2, 12)` |
| 冒号填充率 | 0.106~0.400（p95 0.289） | ≤0.45 |
| 段高 / 行带 | 0.391~0.720 | `(0.35, 0.80)` |
| 冒号上缘 | 0.192~0.391 | ≥0.15 |
| 右侧正文宽 | 60~354（p5 82） | ≥50 |
| 药丸宽 / 填充率 | 45~87px / 0.616~0.903 | ≥40 / ≥0.60 |
| 背景众数占比（q32） | 最低 0.241、中位 0.520 | ≥0.15 |
| 纯英文昵称 | 75/750 = 10% | `skip_pure_en=True` |

冒号左右缝在快手上是 4~18px 的**连续分布**，两簇没分开 ⇒ 两道缝闸都保持 0，
